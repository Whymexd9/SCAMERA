# Vivo upscale migration

## Status

| Backend | Implemented | Still required |
|---|---|---|
| Vivo RAISR 1.1.56 | Experimental isolated worker; real Init/Process/Uninit calls; capture pipeline replaces Nano RAISR; firmware/filter SHA-256 gate; stock ISO-based profile selection; YUV conversion; timeout and original-image fallback | Phone quality validation (RAISR execution reported working, but with fine artifacts); stock color/range parity |
| SoftPQE V2.19.0 | Experimental main-camera ×2 capture path; real Init/Process/GetMode/Uninit; canonical VAF init construction; 21-file SHA gate; bypass/error fallback; backend selector | Device execution, format/range verification, stock capture metadata, visual/latency/memory validation |
| Qualcomm MFSR | Pinned SM8750 registration ABI, ten pipeline stages and factory dependency recovered; registration probe implemented and original entry point emulated | CamX/CHI request/metadata/buffer/session integration; multi-frame capture graph; device execution |

**These are not three completed functional ports.** RAISR and SoftPQE have experimental capture paths. Qualcomm MFSR has no capture path and no enabled setting. Existing SCAMERA RAW MFSR is unchanged and must not be relabelled as Qualcomm MFSR.

## RAISR replacement

`HdrxProcessor` calls `VivoRaisrProcessor` after PostPipeline and before encoding/gain-map processing. The previous Nano RAISR Java CPU/GPU implementations, shader and three filter banks are removed. Old enable/output-scale preference keys remain compatible. Old filter-bank/mode controls remain removed: they are not parameters of this vendor adapter. Strength, texture and halo controls now act on the vendor output in SCAMERA; they are not advertised as internal Vivo parameters. Archived values are retained.

The native executable is generated by `buildVivoUpscaleWorker`, using the same NDK as the neural-remosaic worker. No vendor binaries/weights are added to Git or the APK: this version reads the matching phone firmware via a separate root process. Every job verifies the selected profile, all its filter files, the core library, libc++_shared and libvivolog against the supplied dump before loading them. Modified/different firmware fails explicitly and retains the original image.

Vivo SAT role is not a Camera2 ID. In the pinned RAISR binary, switch table at VA 0x643a0 dispatches role 2 to `raisr_rear_master` and role 8 to `raisr_rear_tele_3x`. The modelPath must be the parent `/vendor/camera3rd/nti/raisr`, not the profile directory. The adapter maps known X200 Ultra Camera2 IDs 3/5 to these roles. Unknown IDs (including wide ID 4) fail with a report; it does not silently use the main-camera profile for the wide camera. This mapping will need extension for custom logical/physical module configurations.

The worker uses a 0x160 init structure and 0x78 VImageEx. Important offsets: height/width 0/4, output height/width 8/12, crop type 0x10, zoom 0x24, role 0x28, modelPath 0x2c, log level 0x130, disable 0x134, ISO 0x138. Image planes 0x10, strides 0x30, scanlines 0x40, byte counts 0x50. The VAF caller at 0x4cd0 passes handle, input descriptor and output descriptor to `vivoRaisrProcess`; Uninit takes the handle directly.

Use crop type 2 for explicit output dimensions. Only 17/18 image formats are accepted by the vendor validator. The experimental app supplies limited-range BT.601 NV21 with code 17 and decodes the same order. The exact vendor enum/color contract still needs device chart validation. Application roundtrip tests cannot prove it.

Inputs/outputs must be even-sized, isotropic 1–4x, within the vendor dimension bounds and a 96 MP application cap. Conversion uses two RGB rows rather than a full additional int[] frame. Output descriptor changes, guard corruption, zero/untouched results, wrong file size, nonzero vendor exit and timeout are failures. The child has a 180-second kernel timeout, client 200 seconds. Reports go to the existing app log and `vivo_upscale_report` preferences. There is no automatic fallback to Nano RAISR, no claim of GPU execution, and no stock-quality certification.

## SoftPQE experimental integration

`pref_vivo_upscale_backend_key` chooses RAISR or SoftPQE under the existing enable preference. Default stays RAISR; the legacy manual scale is disabled for SoftPQE. The shared client invokes the worker with `--softpqe`. The current supported profile is Camera2 ID 3 / SAT master role 2, exact ×2. The original image is kept on root denial, missing/mismatched firmware, unsupported module/size, initialization failure, bypass, process error or invalid output. This is an experimental path, not verified stock-quality processing.

The configuration is the original `config/ui_normal_shot/aigc_24M`, with Y+UV processing and `enableSuperResolution=2`. The original `model` directory contains all nine VDNN models. A 21-file SHA manifest pins the four XML files, nine models, core, VDNN, libc++_shared, vivolog, QNN HTP/System/V79 stub/skel. Other system dependencies must still be ABI-compatible. The ADSP search path is explicitly passed; actual DSP access from the root worker needs a phone test. No weights are copied into the APK.

`vivo-softpqe-abi.h` reproduces all 616 bytes built by VAF at 0x4b80..0x4c20 for the supported metadata. Tests execute those original ARM64 instructions and compare with the compiled C++ builder for three dimension/gain combinations. Init copies this block to handle+8. Init offsets: height/width 4/8, output height/width 0x10/0x14, bit depth/role 0x30/0x34, zoom 0x40, sensor gain 0x64, DRC gain/UI zoom 0x70/0x74, config/model pointers 0x100/0x108, crop 0x240..0x24c, quad 0x250, digital zoom 0x254, optional pool 0x260.

Process takes `(handle, processBlock, outputImage)`. The process block has input Image pointer at 0, three zeroed optional mask records at 8, zero count at 0x188, bit depth 8 at 0x190. Core copies 0x194 bytes; natural structure size is 0x198. Output is caller-owned VImageEx, confirmed from VAF 0x5004..0x5024. GetMode reads handle+0x5dcc; bypass byte at 0x5dc8 is also checked before/after Process. A success return while bypassing is rejected.

**Metadata limitations:** at the final Bitmap stage the original Vivo scene/capture metadata is unavailable. Gain is ISO/50 (corrected from ISO/100 after checking core instructions); DRC/UI/digital zoom and two unidentified floating metadata fields are neutral 1.0, full-frame crop, no masks/faces, quad disabled. These choices reproduce a valid wrapper construction but do not prove appropriate tuning for our processed images. The experimental NV21 code 17 / BT.601 limited-range contract, profile suitability, format alignment, model execution and output quality require device verification. Normal mode plus populated output is a validation gate, not proof of stock equivalence.

`tools/vivo-upscale/inspect_qnn_v3.py` retains the nine graph metadata shapes. Y1x has 16 input channels; Y2x/Y4x four; UV five. The adapter delegates packing, tiling and model selection to the actual Vivo core rather than inventing a direct QNN tensor mapping.

## Qualcomm MFSR blocker

The supplied `com.qti.feature2.mfsr.sm8750.so` exports `ChiFeature2OpsEntry` and HWmultiframe feature callbacks, not a standalone image-to-image API. DT_NEEDED includes com.qti.chi.override, CamX utilities/settings/ODS, metadata managers, graphics/buffer and Vivo provider interfaces. The Prefilter/BlendLoop/BlendFinal paths operate on CHI request objects and negotiated formats (including UBWC/P010). Passing an RGB bitmap to the entry point cannot port it. The worker registration probe now calls only `ChiFeature2OpsEntry` and validates its 0x38-byte operations structure. It does not call the factory/query/negotiation callbacks with guessed opaque structures.

For the pinned SM8750 build, registration is VA 0x4f860: size at 0, vendor name at 8, version at 0x10, create/query/vendor-tag/negotiation callbacks at 0x18/0x20/0x28/0x30 (VAs 0x4f8b0/0x4f8c0/0x4fc40/0x4fc50). Original entry-point execution under Unicorn confirms these offsets. The factory allocates a 0x6c8 HWmultiframe object and calls `ChiFeature2Base::Initialize(ChiFeature2CreateInputInfo*)`; query requires a real ExtensionModule/sensor context. Those cannot be replaced by empty allocations.

Ten stage descriptors are present: Prefilter, BlendInit, BlendLoop, BlendFinal, BlendInit_16, BlendLoop_16, BlendFinal_16, Equalization, ML, Postfilter. Four flows cover two-frame, three-frame, Pre64 and Post64 variants. Merely selecting a stage does not provide its sessions, metadata dependencies or buffer managers.

The earlier supplied camera archives also contain the full 6,255,512-byte `com.qti.chi.override.so`; it was examined. `UsecaseSelector::MFSRMatchingUsecase` at 0x57e7a0 returns constant true, so it is not a callable standalone MFSR processor or sufficient activation recipe.

**Remaining integration boundary:** restore the exact CreateInputInfo and stream negotiation contracts, initialize a real CHI context/session and target-buffer/metadata managers, submit an aligned frame series with per-frame capture results/fences, then retrieve the final postfilter output and clean up requests. Alternatively determine a documented-by-binary HAL capture route that constructs this graph itself. No such working route is established yet. The current Camera2/Bitmap pipeline does not supply these objects. Qualcomm MFSR is therefore still not ported as an operational backend.

## 30202 device report: graphics dependency loading failure

The supplied September 19 logs contain three attempts where all 21 firmware hashes pass, followed by `dlopen` failure: system `libgraphicsenv.so` cannot resolve `android::base::Join`. No SoftPQE Init/Process is reached. The launcher incorrectly put vendor directories before system directories in LD_LIBRARY_PATH. Changed to system → system_ext → vendor → vendor/hw, matching the established neural worker's system-first policy. Vendor entry points remain absolute paths and the SHA gates remain intact.

A host dynamic-loader regression reproduces this class of failure using two same-SONAME libraries and confirms resolution with the actual Java launcher's new directory order. Java compilation also checks the launcher. Launch dimensions, backend, library order and exit status now appear in diagnostics. These checks do not establish successful device inference; the repaired APK needs a new phone run.

## SoftPQE session fix and RAISR controls (30204)

The supplied `log-2026-09-19(1).txt` shows that the 30203 system-first loader fix
worked: the core opens, parses XML and loads VDNN model containers. Session creation
then fails at SoftPQE loadModel lines 117/119; Init enters bypass. There is also a
`/vendor/npu/lib/libQnnHtp.so` lookup warning and exit 139 during allocator teardown.
The namespace warning alone is not proof of the entire session failure.

Following the neural-remosaic approach, initialize the exact runtime before model
sessions, keep it alive, validate output and preserve the original on failure.
The upscaler uses firmware QNN 2.28 models, not the remosaic model/runtime binaries.
Call the pinned `vdnnPlatformInitV2(void**, const std::__ndk1::string&)` with
`PLATFORM:SM8750_2_28 APK:1` before SoftPQE. Its real parser and platform map produce
modelType 18 and APK flag 1, matching all nine supplied model headers. The QNN 2.28
runtime is a first-use singleton (0x1e4ef8), so this call must precede model loading.
APK mode selects existing `/vendor/lib64/hw/libQnnHtp.so` and `libQnnSystem.so`
(0x1e50bc/0x1e515c), both SHA-pinned. Stock process-domain defaults are retained.
No namespace, permission, signing or firmware changes are made.

SoftPQE core at 0x90e84/0x90e94 multiplies gain by 50. The previous ISO/100 input
made ISO 287 appear as 143.5 in the supplied log. Supply ISO/50. Explicit algorithm
Uninit and file close precede `_Exit(rc)` in the disposable worker, avoiding vendor
static allocator destruction; errors retain their nonzero status and no success
marker is emitted. Library handles remain mapped until process exit.

RAISR audit: the compiled Init builder matches every one of the 352 bytes emitted
by original VAF fillInitParams at 0x4a88 for 1x/2x/4x, multiple ISO values and both
SAT roles. The earlier original-core validator and native profile-path tests also
remain applicable. This confirms structure/copying/role-path mechanics, not identical
stock processing: input is already processed by SCAMERA, exact color contract and
stock scene metadata remain unverified. No supplied RAISR output image permits a
conclusive diagnosis of the reported worm-like texture.

Three actual output controls, with defaults strength 50, texture 60, halo 70:
- Strength interpolates between half-pixel bilinear input and processed output,
  including chroma. Zero gives ordinary interpolation; it is not super-resolution.
- Texture smooths the enhancement residual using a 3x3 edge-aware neighbourhood.
  The reference edge is not blurred. It can also reduce genuine fine detail.
- Halo limits enhancement against the local reference range. At 100 it introduces
  no new local extrema. Strength 100 / texture 0 / halo 0 preserves raw Vivo output.

Six cached float rows bound extra memory (under 480 KiB at maximum width), rather
than allocating another full-resolution reference image. Controls are disabled
for SoftPQE and use existing module-profile preference keys. Existing saved values
are not overwritten. Descriptor validation now also checks strides, scanlines and
plane byte counts before decoding.

Validation: original ARM64 VDNN parser/platform-map emulation; original VAF RAISR
Init vs compiled C++ byte comparison; host fault injection for platform/Init gain,
bypass, process error, overrun, descriptor and stride changes; ASan/UBSan synthetic
RAISR residual, halo, interpolation, chroma-order and border invariants; Android
Java/resource compilation. These do not execute QNN on a phone and do not prove
that SoftPQE inference or visual quality is now correct on the user's device.

## Follow-up: native RAISR filter selection

`tools/vivo-upscale/check_raisr_profiles.py <extracted-dump>` executes the pinned
core routine at VA 0x8eb8 through its return. TinyXML navigation and libc helpers
are emulated; the zoom/ISO branches and native configuration writes execute from
the original ARM64 instructions. ELF, XML and every selected filter are SHA-checked
against the manifest. This is a configuration audit, not image processing.

Both supplied profiles have `zoomMode=1`. The branch at 0x9114 selects **Z1 for
every accepted input zoom >=1**, including 2x and 4x. The routine stores the filter
group at handle+0x1180 and input zoom divided by that group at +0x1184; those are
distinct from the requested output dimensions. Merely finding Z2/Z4 files in the
dump does not show that the supplied stock configuration uses them. Do not force
these banks or alter firmware XML as an assumed fix for worm-like artifacts.

| Profile | Low ISO | Mid ISO | High ISO | Default white/black tuple |
| --- | --- | --- | --- | --- |
| Main / SAT 2 | <140 | 140–749 | >=750 | 1, 2, 1 |
| Tele / SAT 8 | <90 | 90–399 | >=400 | 2, 1, 1 |

The no-face branch is the one our adapter uses. A positive face count selects the
separate `withFaceEnhance` tuple (2, 6, 6 for Z1); this audit does not justify
inventing face metadata. The test covers 96 combinations: both profiles, 1/1.5/2/4x,
six ISO cases including each threshold boundary, and both face branches. All pass.

No runtime change follows from these results: our worker already delegates this
selection to the original core with actual capture ISO and the pinned per-role
configuration. They rule out an assumed need to switch to Z2 solely because the
output is 2x; they do not rule out inappropriate input color/range, processing-stage
differences, or native tuning as sources of artifacts. No post-30204 device log or
paired RAISR image was available for this follow-up, so SoftPQE session execution
and the visual effect of the new controls remain unconfirmed on the phone.

## Device-confirmed SoftPQE and adjustable processing

`SCAMERA-debug.log(6).txt` supplied after 30206 confirms a complete main-camera
run at ISO 73: QNN Y/UV graph execution, `mode=0 -> 0 process=0`, populated output,
completion marker and JPEG saved. Dimensions are 3072x4096 -> 6144x8192. The user
reports better detail but excessive smoothing. This establishes successful device
execution for that run, not quality equivalence to the stock camera.

Four independent SoftPQE preferences now default to 100 (the verified 30206 look):

| Control | Operation |
| --- | --- |
| Luma denoise | Scale `noise1Level`, `noise2Level`, `maxNoise1Level` in Y and auxiliary-Y parameter tables across every ISO/DRC level and main/portrait/skin config. At zero, keep maximum at least 1e-6 to satisfy the strict max > minimum constraint. |
| Chroma denoise | Scale UV shot-noise min/anchor/max and read-noise values; preserve noise size and downsampling. Some low-ISO rows already have zero chroma-noise settings. |
| Additional sharpening | Scale post-sharpen weights and floating-point `usmStrength`; at zero disable USM in the main config. The pinned profile already disables the other post-sharpen functions. |
| Overall strength | Mix processed Y/UV with the bilinearly enlarged input. 100 keeps native output byte-for-byte; zero is ordinary interpolation at the same 2x dimensions. |

These noise settings condition the native algorithm; zero does not guarantee
removal of smoothing learned by the network. Overall strength provides a separate
way to reintroduce original texture/noise, at the cost of neural detail.
`blurScale`/`minBlurScale` stay at 1 as explicitly required by the supplied SR
profiles. Model weights, quantization, ISO selection and output geometry stay
unchanged. No invented metadata or runtime offsets are used for tuning.

After the existing firmware SHA checks, the worker creates four exclusive,
non-symlink config files in the app-owned per-shot job directory. Only numeric
leaves within the named sections are changed. Init receives this private path;
firmware files are never written. All-100 native controls use the original path.
The app cleans up the copies with the other job files. Diagnostics print all four
controls and the selected config path. Preferences participate in existing module
profiles/copy selection and are disabled when RAISR is selected or upscale is off.

Validation includes all original supplied XML templates at stock, reduced and
zero settings; source byte identity at stock; Y/UV separation, auxiliary-Y and
ISO/blur preservation; mix endpoints/chroma order/buffer guards under ASan/UBSan;
a fake-library full worker run verifying private Init path, untouched source
configs and final mixed output; and Android settings defaults/availability.
The new tuning ranges still require visual evaluation on the phone.
