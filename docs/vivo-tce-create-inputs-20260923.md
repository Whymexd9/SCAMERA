# TCE Create: источник cameraInfo/sceneInfo (продолжение vivo-tce-boundary.md)

Состояние 2026-09-23. Уточняет "opaque camera info"/"opaque scene info" из
`vivo-tce-boundary.md` (`### Create argument producer`). Дизассемблирование
чистое (без телефона), на уже имеющихся локальных донорах.

## cameraInfo (input+0x18a0..0x1907, 0x68 байт) — НЕ opaque

`libvivo_nice_cre.so` (SHA `41b277753f7fedbe4dda1e1c4b76d2086d6e79768904d8a4922b48a0e023e76e`),
адрес `38c384..38c414`: копирует байты `input+0x186c..0x1907` из объекта
`x8 = *(*(this+0x9b0)+8)` напрямую (ldr/str парами, без трансформации) в
create-аргумент. То есть это ПРЯМАЯ копия поля из "input"-объекта — того же,
что и `deltaEV` (input+0x1814) / `lux` (input+0x1860) из уже задокументированной
таблицы `NICEIntegration::fillInputParams` в vivo-tce-boundary.md. Значит
"input" в create-продюсере CRE и "input" в fillInputParams — один и тот же объект.

Источник самого input+0x18a0.. — `libvivo.vaf.algo.nice.so`
(donor `libvivo.vaf.algo.nice.so`, в архиве `evidence/inspect/stock/SCAMERA-port-libs.tar.gz`),
адрес `0x10dcc..0x10e40`:

1. `0x10dcc..0x10e18`: весь диапазон `this+0x18a0..0x1958` (шире, чем один
   cameraInfo) обнуляется (`movi v0.2d,#0; str q0,...` семь раз подряд).
2. `0x10e1c..0x10e20`: `this+0x18a0` = `config+0x374c` (int32) — то же
   "config"-подобный объект (`x22`), что фигурирует в vivo-tce-boundary.md
   как источник `config+0x5ec8`/`config+0x55cc`/`config+0x5a4c`/`config+0x5eac`.
   Это похоже на per-camera/tuning конфигурацию, не на per-shot AE-состояние.
3. `0x10e24..0x10e3c`: ещё один блок копируется из `x9+0xcd8` (вычисляемый
   указатель, база `x22+0x6d000`) в `this+0x18a4..` через `ldp q/stur` —
   массовое копирование ~0x30+ байт из того же config-объекта.
4. Отдельно `this+0x189c` (сразу ПЕРЕД cameraInfo, вне заявленного диапазона
   0x18a0..0x1907, но в непосредственном соседстве) = `x26+0x70` — другой
   объект (`x26`), не `config`; требует отдельной идентификации.

**Вывод**: cameraInfo — это в основном нули + копия статического
per-camera/tuning блока конфигурации (`config`, `x22`). Это НЕ то же самое,
что stock-приложение-only UI/session state (как в случае с полным
`selectNiceScene`, см. `vivo-nice-scene-selector.md`) — конфигурация камеры
теоретически восстановима из `CameraCharacteristics`/статических tuning-файлов
(`/odm/etc/vas/nice2.0/*`, уже частично извлечены — `vivo-nice-tuning.md`),
а не только из живого стокового процесса.

## sceneInfo (input+0x186c..0x188b, 0x20 байт) — источник НЕ найден в этой библиотеке

Поиск записей по офсетам `0x186c,0x1870,0x1874,0x1878,0x187c,0x1880,0x1884,0x1888`
в `.text` `libvivo.vaf.algo.nice.so` дал 0 совпадений (при том, что соседний
cameraInfo найден сразу). Значит sceneInfo пишется либо через промежуточный
регистр с иначе вычисленным базовым смещением (например
`add x9,x19,#0x1800; str w0,[x9,#0x6c]` вместо прямого `[x19,#0x186c]` —
компилятор мог разбить офсет), либо в ДРУГОЙ функции/библиотеке. Не проверено:
`libvivo.vaf.system.so` (там же, где `ICInputPreProcess`/`36fa34` и парный
`refEv0EV` расчёт, судя по соседним офсетам `0x116c` в том же файле). Следующий
шаг — повторить тот же поиск (STR по разбитым офисетам, с учётом промежуточных
`add`) в `libvivo.vaf.system.so`.

## Ограничения находки

- Это чистая статика, ничего не проверено на реальном устройстве в рамках
  этого документа (нет офсетов "живых" адресов, только структура кода).
- `config` (x22) и `x26+0x70` объекты сами не идентифицированы — только
  установлено, что они не являются per-shot AE-данными и не тем же объектом,
  что "input"/"parent".
- Не доказано, что `CameraCharacteristics` действительно достаточно для
  восстановления всех полей `config+0x374c`/`x9+0xcd8` — только предположение
  по характеру данных (обнуление + блочное копирование конфигурации).
- Полное поле-в-поле сопоставление (что именно лежит в каждом из ~26 int32/
  float слотов cameraInfo) не выполнено — нужно продолжить трассировку
  потребителей внутри TCE Process (кто и как читает эти поля из
  CreateArgument после копирования), аналогично уже сделанному для
  deltaEV/lux в vivo-tce-boundary.md.

## Следующие шаги

1. Найти источник sceneInfo в `libvivo.vaf.system.so`.
2. Проследить потребителей cameraInfo/sceneInfo ВНУТРИ TCE (`libvivo_nicetce.so`,
   SHA `9f5deac3bc68fc86fcf16b98f43c232a9642bc309c7d5d42c88d6a4b596b892d`) —
   что физически меняется в тонмаппинге при разных значениях этих полей;
   без этого нельзя понять, насколько приближение через CameraCharacteristics
   будет визуально корректным.
3. Идентифицировать объекты `config` (x22) и источник `x26+0x70`.
