# runtimeRatio (params+0xe0): точный найденный источник в com.vivo.stats.aec.so

Состояние 2026-09-22, без подключённого телефона — чистое статическое
дизассемблирование уже имеющегося локального `com.vivo.stats.aec.so`
(SHA-256 `b2e3e12469a05cf62c2a5892b2b619228fb29a3ccb8fa9fe5f934df0dd5842e9`,
подтверждён идентичным установленному на телефоне в этой же сессии до
отключения телефона). Инструмент: `local-tools/disasm.py` (capstone+pyelftools).

## Живой эмпирический факт (получен ДО отключения телефона в этой же сессии)

166 подряд реальных вызовов `VivoRawHdrExpCalc::vivoCalculateExpInfo`
(`_ZN17VivoRawHdrExpCalc20vivoCalculateExpInfoEP23VivoRawhdrProcessParamsPN4IVAE23VivoRawhdrProcessResultE`,
экспорт по адресу `base+0x178808`) на стоковой камере (runMode=11,
sceneMode=0xc00000) дали params+0xe0 = ровно 4.375407695770264. После
одного тапа метеринга по тёмной области следующие 49 вызовов (тот же
runMode/sceneMode) дали ровно 3.9092330932617188. См.
reports/live-ae-20260922/ и раздел HANDOFF.md за 2026-09-22.

Значение также присутствует байт-в-байт по адресу `this+0x638` в самом
объекте `VivoRawHdrExpCalc` (`calculator` в observer.js читается как
`object.add(0x5f0)`, 0x5f0+0x48=0x638) — то есть params.runtimeRatio это
копия object->0x638, сделанная где-то до вызова (сам params — отдельная
структура, передаваемая вызывающим кодом).

## Дизассемблирование: где именно пишется object+0x638

Единственная во всей `.text` (284274 инструкций) запись `str s.., [Xn, #0x638]`
находится по адресу `178708-0x178808` (сразу перед экспортом
vivoCalculateExpInfo, то есть это хвост ПРЕДЫДУЩЕЙ функции по тому же адресу
диапазона, видимо вспомогательный сеттер/подготовка, вызываемый перед
основным расчётом). Полная трасса (`x19`=this):

```
17870c: bl #0x1eacb0      ; PLT -> VivoRawHdrExpCalc::getNeededFrameHistory()
178710: mov x20, x0       ; x20 = frameHistory*
...
1787d0: ldr s0, [x20, #0x6bc]   ; s0 = frameHistory->at(0x6bc)  (float)
1787d4: str s8, [x19, #0x63c]   ; this->0x63c = s8 (см. ниже, другое поле)
1787d8: str s0, [x19, #0x638]   ; this->0x638 = frameHistory->0x6bc  <-- ИСТОЧНИК runtimeRatio
```

PLT-таргет `bl #0x1eacb0` разрешён через `.rela.plt`/`.dynsym` на
`_ZN17VivoRawHdrExpCalc21getNeededFrameHistoryEv` (проверено чтением
релокаций GOT-слота 0x1fb6b8, не предположение по соседству адресов).

Соседние поля того же `frameHistory` (x20) в этом же блоке:

| Offset в frameHistory | Тип | Куда копируется (this) |
| --- | --- | --- |
| 0x688 | float | this+0x560 |
| 0x698 | int64/ptr | this+0x558 |
| 0x6b0 | float | this+0x558+0xc = this+0x564 |
| 0x6bc | float | this+0x638 (= runtimeRatio) |

Это кластер из 4 полей одного объекта «needed frame history» с шагом,
не совпадающим с шагом строки TuningBank (24 байта/строка в уже
захваченных bank/alternateBank) — то есть это отдельная, ещё не
восстановленная структура истории AE, а не строка тюнинг-таблицы.
Название метода (`getNeededFrameHistory`) прямо говорит, что источник —
история последних кадров AE, а не статическая таблица и не мгновенный
единичный расчёт сцены. Это объясняет наблюдаемое поведение: значение
стабильно, пока не меняется реальное состояние экспозиции/замера (история
не обновляется резко), и пересчитывается при новой сходимости AE.

## getNeededFrameHistory(): уже дизассемблирован (адрес 0x1785bc, 168 байт)

```
1785d0: ldr x0, [x19, #0x550]     ; x0 = this->0x550 (общий "интерфейс истории")
1785d8: ldr x8, [x0]; ldr x8,[x8,#0x78]; blr x8   ; вызов vtable[0x78](interface, w1=1)
1785e4: mov x20, x0               ; x20 = результат — это и есть frameHistory
1785e8..1785fc:                   ; тот же vtable[0x78](interface, w1=0) — проверка на error/ассерт-путь
178650: mov x0, x20; ret          ; штатный путь просто возвращает x20
```

Значит `getNeededFrameHistory()` в штатном случае — это
`this->historyInterface->at(slot=1)` (вызов через vtable с аргументом 1,
а не собственный расчёт). Ветка с `w1=0` и вызовом `bl 0x1e8a10` (похоже на
CHX_LOG/assert: адреса форматной строки + номер строки 0x1c8=452) — это
путь диагностики при неожиданном ненулевом «slot 0», не основной поток.

Это подтверждает: значение — это slot **1** кольцевого буфера истории AE
результатов, а не мгновенный пересчёт и не статическая таблица. Сам
`this->0x550` — общий указатель на интерфейс истории, используемый и в
других местах той же функции (см. трассу выше, тот же 0x550 читается для
vtable+0x218, +0x298, +0x60, +0x168 — разные акссессоры одного менеджера
истории/сцены). Реализация vtable[0x78] (сам ring-buffer) физически лежит
не обязательно в этой библиотеке — дальнейшее дизассемблирование требует
либо символа vtable-таблицы объекта по адресу this->0x550 (не восстановлен),
либо живого runtime-дампа указателя (нужен телефон).

## Что ещё НЕ сделано (следующие шаги)

1. Восстановить фактический тип/vtable объекта по `this->0x550` (без
   телефона тяжело — нужен RTTI/vtable dump или живой указатель).
2. Найти, ГДЕ slot 1 истории заполняется новым значением между кадрами
   (другой метод класса или другого объекта, вызываемый раньше в
   конвейере при получении нового AE-результата) — это и есть источник
   «формулы», если нужен самостоятельный пересчёт без стока.
3. Подтвердить на живом устройстве (когда телефон снова подключат), что
   указатель `this->0x550` стабилен между кадрами одной сессии, и по
   желанию расширить observer.js accessor-хуками на vtable[0x78] с двумя
   разными аргументами (1 и 0), аналогично уже работающим accessor на
   0x298/0x300/... — тогда можно будет захватывать frameHistory целиком,
   а не только его смещение 0x6bc, и увидеть его эволюцию по кадрам.

## Практический вывод для брекета

Уже подключённый в проекте путь (params+0xe0 читается напрямую из
захваченного `input`, 0xe8 байт) — ПРАВИЛЬНЫЙ и достаточный: не нужно
самостоятельно пересчитывать runtimeRatio, если удаётся получить настоящий
живой `params`-снапшот с mode=9 при реальном стоковом вызове (через тот же
production observer.js). Проблема не в формуле — она уже корректно и
побайтово скопирована в имеющемся коде (`vivo-aec-solver.h`/`vivo-aec-wire.h`).
Проблема только в том, чтобы ПОЛУЧИТЬ настоящий mode=9 (0xc80000) сэмпл
на живом устройстве (см. HANDOFF: нужна более контровая сцена) — этот
документ не меняет тот вывод, только подтверждает, что подстановка
константы вместо живого захвата была бы ошибкой (значение честно меняется
кадр-к-кадру по истории AE, а не по формуле от sceneMode/mode).
