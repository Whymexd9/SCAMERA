# SCAMERA ZSL/AE/NICE live v21

v6 проверена трассой `30Hy1RcT`: NICE и обе очереди вернулись,
PID provider 28598 сохранился. Получение будущего кадра v6 не наблюдала.

В трассе v7 VvrJ8241 план и подготовка обеих очередей записаны, PID сохранился,
но ни входа, ни выхода getPastAndNextBuffers нет. Это не доказывает потерю кадра.
v8 наблюдает экспортированные getPastAndNextBuffers (0x12bb14), getPastBuffers
(0x128734) и getNextBuffers (0x129f50) в libvcf_session.so.
Записываются ограниченные векторы shared_ptr и ID, без чтения пикселей
или вызова методов буферов. Наблюдаются все очереди в ограниченном окне;
knownQueue отмечает связь с ранее наблюдавшейся подготовкой.
Вектор BufferPrepareInfo по queue+0x270 имеет шаг 144; он остаётся сырыми байтами.
Окно наблюдения — 30 секунд после первого плана NICE, общий предел агента — 60 секунд с запуска,
резервный предел оболочки — 70 секунд. Завершение окна не означает завершение серии.

## Дополнительные входы AE в v21

`ae-tuning.js` наблюдает реальные вызовы таблицы экспозиций и коррекции
нормальной/длинной экспозиции внутри vivoCalculateExpInfo. Сохраняются выбранные
строки таблицы, вход и результат расчёта, параметры движения и подавления
мерцания. Привязка идёт по вложенному вызову и потоку, а не по близкому времени.
Таблица с изменившимися байтами получает новый ID, даже если её адрес прежний.

Наблюдение не меняет настройки камеры, не читает пиксели и не вызывает методы
AE. Ограничения: 60 секунд, 4096 вызовов решателя и 4096 подробных расчётов,
128 уникальных таблиц, до 1024 строк каждой, не более 8 МиБ новых событий. Ошибки и превышение границ остаются
в логе. Основная часть trace.js сохраняет формат v20; новые события имеют v21.
Это сбор входных данных, а не готовый перенос и не доказательство соответствия
Camera2 ISO нативному gain. Один снимок стоком: Фото, 1×. Прислать архив целиком.

## Анализ

v9 дополнительно проверяет SHA256 `com.vivo.stats.aec.so` и перехватывает
экспорт `VivoRawHdrExpCalc::vivoCalculateExpInfo` (0x178808). К событию затвора
сохраняются 8 предыдущих результатов AE и до 120 последующих. `ae_result`
содержит входной блок, общие настройки, флаги и выходные записи. Это результаты
расчётчика: их время не доказывает соответствие конкретному RAW или frame ID.
Обычный analyze.py продолжает разбирать очередь. analyze_ae.py дополнительно
читает шесть записей AE, проверяет EV через произведение выдержки и усиления
и показывает ближайший предшествующий затвору расчёт отдельно от плана кадров.
Полная готовность требует подключения AE, NICE и очереди. Прошивка и сенсорный
режим не меняются; правило SELinux остаётся тем же, что описано ниже.

```sh
python3 analyze.py scamera-zsl-trace.XXXXXXXX.tar.gz
python3 analyze_ae.py scamera-zsl-trace.XXXXXXXX.tar.gz
node check_trace.js
python3 check_runner.py
```

Анализ разделяет query/произведённый план, очередь и выдачу буферов.
`futureDeliveryObserved` требует известной очереди, возврата 1, роста future-вектора с ненулевыми
указателями и сохранения его прежнего префикса. Это не проверка содержимого RAW,
экспозиций или входа нейросети. ID общие для нескольких очередей, повторы нельзя
считать новыми временными кадрами. Native gain/shutter не переводятся в Camera2.

В 30Hy1RcT: alternateExposureMode=true, 4 past + 1 future; future EV=100,
gain/shutter=0. Catch mode при возврате NICE=4, при подготовке очереди=6.
Эти различия не подменяются постоянными настройками.

В трассе v8 CqyFNMG0 подтверждены 4 past (ID 63..66) + 3 future
(83..85), коды −100/−200/100, producer catch mode 4 и queue catch mode 6.
Выдача future подтверждена анализатором; фактические выдержки/ISO и
содержимое RAW эта трасса не фиксирует. Это наблюдение конкретного снимка,
а не постоянный план для всех сцен.

## v12: два процесса

BscaFS2x: план 4 past + 1 future (код 100), очереди выдали ID 62–65 и 81.
В Qualcomm PID 1832 алгоритм NICE отсутствовал. Последующее чтение maps
показало libvivo.vaf.algo.nice.so в camera3rd PID 1934 с контекстом
u:r:hal_camera3rd_default:s0. PID не зашиты: выбираются точные имена процессов
и проверяются библиотеки и контексты до запуска.

v12 одновременно запускает capture (AE/ZSL, Qualcomm) и nice_inputs (camera3rd).
Второй наблюдатель не ждёт локального nice_enter: этот запрос происходит
в другом процессе. Он пишет максимум 24 пары вход/выход за окно наблюдения.
Снимок разрешается после ready обоих наблюдателей. После первого плана
Qualcomm остаётся 30 секунд; затем оболочка завершает оба инжектора.
Общий предел каждого агента 300 секунд, оболочки 310 секунд.

В дополнение к прежнему правилу применяется
`allow hal_camera3rd_default tmpfs file { read write open getattr map execute }`.
Оба правила относятся ко всем tmpfs:file для соответствующего домена,
действуют до перезагрузки; Enforcing сохраняется. Постоянных модулей нет.

capture.log и nice-inputs.log сохраняются отдельно; trace.log содержит
их конкатенацию. PID и время сохраняются, адреса разных процессов не
сравниваются как идентичность кадра. Наблюдение NICE одновременно со снимком
само по себе не доказывает принадлежность этому снимку. Если входов нет,
это не доказывает отсутствие обработки: camera3rd может обслуживать иной путь.
Пиксели не читаются, экспозиция и режим сенсора не изменяются.

Проверено на хосте: роли перехватов, запись входа без локального запроса,
границы памяти, запуск двух процессов, отказ второго подключения/правила,
приглашение после двух ready, объединение логов и очистка. В присланных
RvYoEiAn и SQGhYcUe v12 записал по семь входов NICE; идентичность
сенсорных кадров между процессами эти трассы ещё не устанавливают.


## v13: идентификаторы буферов между процессами

Добавлено чтение `/proc/self/fdinfo` для поля NICE image+0x68 и дескрипторов
native_handle из BufferInfo+0x10. Расположение handle подтверждено
holdMetadataLocked (libvcf_session.so 0x12e08c..0x12e0d8): запись pending
ищется по ID +0x24, затем handle используется ключом карты метаданных.
Поле NICE+0x68 копируется в CRE+0x28 (0x10ae8..0x10aec).

Идентификаторы читаются в момент наблюдения, не после окончания съёмки.
Лимиты: 1024 чтения fdinfo, 8192 символа на файл, 128 записей на очередь,
8 FD и 128 целых на native_handle. Ошибки чтения сохраняются в логе.
Пиксели и метаданные камеры не изменяются; дополнительные правила SELinux
не применяются. Анализ: `python3 analyze_buffer_identity.py <архив>`.

Анализатор сопоставляет inode, размер и имя экспортёра DMA; номера FD и
виртуальные адреса не используются для соединения процессов. Совпадение
объекта ещё не доказывает идентичность сенсорного кадра: буфер может
использоваться повторно. Неоднозначные совпадения сохраняются как кандидаты.
Нужен один снимок в стоковой камере после приглашения сборщика.

## v16: возвращённый буфер вместо старой записи очереди

В delivery_leave добавлены pastIdentity/futureIdentity: объект читается из
возвращённого shared_ptr, проверяется vtable PlatformImageBuffer (0x235788+16)
и хеш libvcf_platform_utils.so. Порт чтения getBufferHandle (0x18b890)
выбирает внешний слот +0xe0 либо встроенный +0xd8 и разыменовывает слот.
Методы камеры не вызываются, пиксели не читаются. Неизвестный тип отклоняется.

Анализатор отдельно показывает returnedBufferCandidates. Для одиночной успешной
выдачи он проверяет указатель объекта против возвращённого вектора и использует
возвращённый ID. Старый ID из снимка ready не заменяет текущий. При нескольких
кадрах/ID привязка этим анализатором не устанавливается. DMA по-прежнему не
доказывает timestamp сенсора. В v15 этих наблюдений не было: повторный анализ
старого архива не восстановит отсутствующие данные. Лимит остаётся 60 секунд.

После анализа 9wS3Z6Ih добавлены observedWindowCandidates/observedWindowStatus:
только выдачи до входа NICE и после последнего наблюдаемого prepare той же
очереди. Совпадения с одинаковым timeMs между процессами не упорядочиваются.
returnedBufferCandidates сохраняет всю историю, включая повторное использование
DMA. Старое поле status относится только к queueCandidates. Временное окно —
диагностическая гипотеза, а не доказательство sensor timestamp/capture identity;
перекрывающиеся серии и пропущенные события могут сделать его неверным.
В двух сериях этого архива найдено по семь кандидатов внутри окон; 84 копии
полей AE и 14 указателей совпали. Обновление анализа не требует нового запуска
сборщика на телефоне и не меняет опубликованный архив v16.


## v17: метки сенсора и объект Metadata

На выдаче одиночного RAW читается карта native_handle → Metadata в BufferQueue
(+0x2f0, первый узел +0x300; next +0, key +0x10, metadata +0x18). Обход ограничен
256 узлами и отклоняет циклы/неоднозначность. Основание — holdMetadataLocked
0x12e024 и обход той же карты в getOffset 0x142dc0 в проверенной libvcf_session.so.

Пассивный hook MetadataImpl::getMetadataByTag(uint32_t,bool) по 0xa7a88
libvcf_platform_utils.so записывает естественные чтения стока. Проверено по
0xa7b98..0xa7c8c: платформа возвращает тип/count в x0 и data в x1; MetadataImpl
проверяет тип и возвращает count в x0, data в x1. Сборщик не вызывает getter сам,
не изменяет запросы, не копирует пиксели и не записывает память камеры.

Теги: sensor timestamp 0xe0010/int64, exposure time 0xe0000/int64,
sensitivity 0xe0002/int32, request frame count 0xc0000/int32. Определения:
https://android.googlesource.com/platform/system/media/+/refs/heads/main/camera/include/system/camera_metadata_tags.h
Не следует считать request frame count равным внутреннему ID очереди.
Хранятся последние 64 чтения до выбора серии и не более 512 после выбора.
Чтение значения выполняется только при count=1, ошибки чтения записываются.

Анализ: python3 analyze_sensor_metadata.py <архив>. Он сохраняет точные int64,
отделяет PID, показывает все наблюдаемые значения Metadata и повторное использование.
Не выбирает timestamp по ближайшему времени. Объект Metadata может обновляться;
карта и поля не являются атомарным снимком. Отсутствие metadata_read означает,
что пассивный hook не наблюдал нужное чтение, а не отсутствие timestamp у RAW.
Это сбор данных для подключения; production RAW/AE ещё не подключён к
CaptureController. Нужен запуск v17: один снимок на сток, прежний лимит 60 секунд.


## v18: квота на серию и vendor AE

Ns4zIwxa (v17) содержит две серии по 7 RAW, но 512 live-чтений метаданных
исчерпаны примерно за 0.9 секунды: повторные чтения preview заняли квоту.
Повтор одинакового значения одного тега/объекта теперь подавляется (LRU 256).
Каждый prepare восстанавливает квоту 512; общий предел 4096 записей сохраняет
ограничение объёма за запуск. Предел съёмки остаётся 60 секунд.

Добавлен пассивный hook строкового MetadataImpl::getMetadataByTag по 0xa7cc0,
символ _ZN3vcf12MetadataImpl16getMetadataByTagEPKcS2_b. Он разрешает имя и
в 0xa8038 вызывает числовой getter через vtable+0x78, возвращая тот же count/data.
Читается только vivo.control.Vivo3rdAlgoAECFrameControl, ровно 35 float (140 байт).
Имена ограничены 96 ASCII-байтами. Несовпадение count сохраняется без чтения данных.
Анализатор хранит vendor AE отдельно от стандартных полей, включая исходные байты.

Причина: у normal RAW первой серии Ns4zIwxa standard exposure=9999996 ns,
а на входе NICE exposure=3.601474 ms и gain=27.208839. Причина расхождения ещё
не установлена. Нельзя считать стандартное поле правильной заменой vendor AE
или переносить одну и ту же поправку на остальные кадры. Новый hook наблюдает
чтения стока, не вызывает методы камеры и не меняет её память/запросы.


## v19: фактическое копирование VAS RAW AE

Hook VASAdapterMetadataConvertVCF::getMetaData(void*,uint32_t,void*,size_t),
экспорт _ZN28VASAdapterMetadataConvertVCF11getMetaDataEPvjS0_m, адрес 0x6155c.
Дизассемблирование 0x6155c..0x615ec подтверждает args: this, source, tag,
output, bytes; возврат bool=1 означает выполненное копирование в output.
Для vendor AEC разрешён только returnAddress=base+0xdcd2c и размер 140 байт.
Для стандартных timestamp/exposure/sensitivity разрешены только правильные
размеры 8/8/4 и caller внутри convertRawshotMetadataIn 0xdbaac..0xe7c40.
Читается результат только успешного вызова; максимум 256 событий отдельно
от лимита общих MetadataImpl-чтений. Данные source пока не объявляются объектом
Metadata из очереди — эта связь требует подтверждения. Методы камеры не
вызываются сборщиком. Анализатор выводит vasRawMetadata отдельно.

Поддерживаются два снимка за запуск. Лимит остаётся 60 секунд. V19 не меняет
сессию камеры, sensor mode, обработку или CaptureController. Завершённого
production RAW producer по-прежнему нет; данный архив не является APK.

## v20: AE и timestamp одного преобразования RAW

В v19 скопированный vendor AE принадлежит другому объекту Metadata, чем
снимок карты очереди. Общие чтения Metadata содержат timestamps этих объектов,
но объекты переиспользуются. Склеивать такие наблюдения по времени нельзя.

V20 перехватывает экспорт convertRawshotMetadataIn (0xdbaac) и ведёт стек
вызовов отдельно для каждого потока. Записывает VCFProcessRequest, его
input_frames (до 20 записей по 0x98 байт) и источник Metadata по +0xa8.
Копия AE получает идентификатор этого вызова только при совпадении источника.

Timestamp читается стоком через VASAdapterMetadata::getMetadata (0x12884c),
а не через getMetaData с копированием. Отслеживается только tag 0xe0010,
returnAddress=0xe1950, совпавший источник и активный поток преобразования.
После успешного чтения копируются восемь байт по возвращённому указателю.
Никаких дополнительных вызовов Metadata и чтения пикселей нет.

analyze_vas_binding.py выдаёт связку VCF request/frame → использованные AE и
sensor timestamp только после возврата того же вызова. Отбрасывает пропуски,
повторы, чужой поток, замену источника и изменение заголовка запроса.
Дескрипторы input_frames пока остаются непрозрачными: эта связка сама по себе
не доказывает передачу пикселей в SCAMERA или связь с входом NICE другого PID.

Лимит — 32 преобразования и 60 секунд. Тесты включают вложенные вызовы,
переиспользование адресов и timestamps больше 2^53. Проверка v20 на телефоне
ещё требуется. CaptureController и production RAW transfer пока не подключены.
