# Bento в гибридном слиянии Sabre (SCAMERA): как это устроено, со всеми нюансами

Документ описывает **работающую** реализацию Bento (восстановление клиппированных светов ультракоротким кадром) в
LMC-гибриде SCAMERA (Sabre 6.1 kernel × LMC 9.6 rejection/weights × Bento × Shasta) — от планирования съёмки до
тон-маппинга. Состояние кода — рабочее дерево на 8 октября 2026 (только чтение; код не менялся).

## 1. Зачем Bento и где он стоит в снимке

### 1.1 Назначение

Нормальные кадры серии (N) экспонированы по превью-AE и в ярких местах (лампы, окна, небо, экраны) клиппируются.
Bento добавляет к серии 1–2 кадра с экспозицией в k раз меньше (по умолчанию k = 8) и **заменяет** ими клиппированные
области базы: внутри маски светов база и все остальные кадры теряют вес, сливаются только ультракороткие кадры, умноженные на
k (приведённые к единицам базы). Поэтому выход слияния в светах уходит **выше 1.0** (до ≈ k·белого) — это реальные данные о
яркости, которые дальше использует восстановление светов и тон (ARK) [код: шапка `H:11-13`; `H:1016-1017`; §5].

### 1.2 Маршрут

Bento существует только в маршруте «LMC hybrid» (`pref_merge_route = hybrid`): Java собирает серию NCH v10
(`LHB`), воркер (`W:174-203`) вызывает `vivo_nice::hybridReconstruct` (`H:4763`). Путь SCAM HDR (нейросеть NICE)
Bento не использует; при откате SCAM HDR → hybrid (`HdrxProcessor.java:479-493`) кадры S/ES NICE-серии превращаются в
роли гибрида функцией `hybridFromNiceBurst` (`H:6540`): из слотов 5/6 ультракоротким (роль 5) становится тот, чья экспозиция
ближе всего к 1/8 (`H:6555-6561`) [код].

### 1.3 Планирование съёмки (`HybridPlan.build`, `HP:96-134`)

Вызывается из `CC:4161-4180` после нажатия, когда N-кадры уже лежат в ZSL-кольце [код]:

1. **N-экспозиция** — метаданные самого нового кадра кольца (`mNativeZslBase`), иначе план `stockPlan` (`CC:4163-4168`).
2. **Доля клиппинга** `mLastZslClipFraction` — `zslClipFraction()` (`CC:3649-3683`): самый новый RAW кольца с «плоским»
   16-битным payload (до 4 кандидатов), выборка каждой 8-й строки и каждого 4-го столбца, доля отсчётов
   `≥ 0.95 × SENSOR_INFO_WHITE_LEVEL` (сырые коды, **без** вычитания чёрного; `CC:3665-3678`). Ошибка/нет плоского RAW → 0.
3. **Режим Bento** `bentoMode()` = `pref_lmc_hybrid_bento` (0 выкл, 1 авто, 2 всегда; `HP:77`; XML-умолчание `"1"`,
   `XML:10`). Условие запроса ultrashort-кадров (`HP:106`):
   `bento == 2 || (bento == 1 && clipFraction > bentoTriggerClip())`, где `bento_trigger` = 0.0005 (`HP:85`, `XML:15`,
   диапазон 0..0.1 в коде, 0..0.02 на ползунке). Иначе в описании плана — `bento off` / `no clipping (%.4f)` (`HP:113`).
4. **Целевая экспозиция**: `target = n / factor`, `n = nShutterNs · nIso`, `factor = ultrashortFactor()` =
   `pref_lmc_hybrid_bento_factor` ∈ [2, 16], умолчание 8 = LMC `ultrashort_tet_factor` (`HP:79`, `PK:786`, `XML:14`).
5. **Сначала gain, потом выдержка** (`HP:108-109`):
   `iso = max(ISO_min, min(nIso, round(target / nShutterNs)))`,
   `ns = max(T_min, min(nShutterNs, round(target / iso)))`. Т.е. ISO опускается вплоть до минимума сенсора, остаток
   добирается укорочением выдержки, но не ниже `SENSOR_INFO_EXPOSURE_TIME_RANGE.lower` (`capped()` режет только верх,
   `HP:170-177`).
6. **Фактическое отношение** `ratio = ns·iso / n`; кадры добавляются только если `ratio < 0.5`, иначе
   `" us skipped (sensor floor)"` (`HP:110-112`). На упоре в минимальную выдержку реальное k меньше заданного (пример §9.2:
   заказано 16, получилось 7.21).
7. **Число кадров** `bentoFrames()` = `pref_lmc_hybrid_bento_frames` ∈ {1, 2}, умолчание 2 (`HP:84`, `XML:11`). LMC 9.6
   снимает один; второй кадр той же экспозиции уполовинивает шум замены и заполняет решётку R/B за счёт дрожания руки
   (комментарий `HP:80-83`).
8. **Порядок запросов**: ultrashort **первыми** (ближе по времени к буферизованной базе), затем bracketed (`HP:28`,
   `HP:104-129`). Если добавлять нечего — один лишний N (`HP:131`).
9. **Запрос камеры** (`HP:205-220`): `CONTROL_AE_MODE_OFF`, `CONTROL_ENABLE_ZSL=false`, явные `SENSOR_EXPOSURE_TIME` и
   `SENSOR_SENSITIVITY`. Для гибрида AF/OIS/EIS/intent/NR/edge/hot-pixel копируются с превью (`CC:4186-4195`: иначе на PHY110
   объектив сдвигался и «ультракороткие света были мягкими»). Тег `NiceCaptureTag(..., r.role)`; в `fullpairs`
   `isHighlightFrame = SHORT || EXTRA_SHORT` (`CC:4200-4210`).
10. **ZSL vs будущие кадры**: N — из ZSL-кольца (прошлое, до `zsl_frames` = 30), ultrashort и L — **будущие** запросы после
    нажатия. С пустым кольцом — `buildNormalBack` (`HP:141-166`): N после затвора, затем те же extras из `build`; без
    известной N-экспозиции — `autoExposure` (только N через AE камеры, без Bento; `HP:188-192`).
11. **P27-классификация пришедшего кадра** `classify` (`HP:227-247`): если фактическая экспозиция отличается от плана
    больше чем на 0.4 EV, роль назначается по отношению к N: `≤ 0.5` → EXTRA_SHORT, `≥ 1.5` → LONG, `[2^-0.5, 1.035]` → NORMAL,
    иначе кадр выбрасывается.

### 1.4 Роли и сборка серии (`LmcHybridBurst`)

* Роли в протоколе NCH v10: `ROLE_NORMAL = 1, ROLE_BRACKETED = 3, ROLE_ULTRASHORT = 5` (`LHB:31`), совпадают с
  `HybridRole { kRoleNormal=1, kRoleBracketed=3, kRoleUltrashort=5 }` воркера (`H:45`) и с `BurstFrameType` LMC
  (3 bracketed, 5 `kUltraShortExp`; `AUD` §3.1) [код/док]. В Java роль ultrashort — `ImageFrame.CaptureRole.EXTRA_SHORT`.
* Кадры раскладываются на N / LONG / «короткие» (`LHB:169-175`). База — самый резкий из 4 новейших N в окне 205 мс
  (`BASE_CANDIDATES = 4`, `BASE_WINDOW_NS = 205 ms`, `LHB:32-33`, `LHB:208-218`).
* Порядок в серии: база (индекс 0), остальные N от новых к старым, bracketed, ultrashort последними (`LHB:218-266`).
* Отбор ultrashort (`LHB:243-266`): короткий кадр с отношением к базе `≥ 0.75` либо идёт как N (если в полосе
  `[2^-0.5, 1.035]`), либо выбрасывается; остальные сортируются по близости к `ref / ultrashortFactor()` (по |log|), берутся
  до `bentoFrames()` штук, у которых отношение `< 0.75` и экспозиция в пределах ×1.3 от первого (`LHB:263`).
* `exposure` каждого кадра = `(measuredExposure · measuredIso) / (то же у базы)` (`LHB:278-285`, `product()` — `LHB:290`);
  кадры вне ×1/512..×512 выбрасываются. `orderMs = (timestamp − newest) / 1e6` — время относительно **самого нового** N
  (`LHB:286`; у ultrashort оно положительно — они сняты после кольца) [код].
* Запрос clip-flags трейлера: `clipFlags = hybridSwitch("clip_flags", true) && highlight_recovery > 0` (`LHB:101`).

### 1.5 Порядок кадров и временные метки (что видно в логе)

[лог LOG15, снимок 14:01:40] Кольцо отдало 30 N (`ZSL shutter cutoff=128156227841192`), затем:
`request=0 role=EXTRA_SHORT ... exposureNs=224319 ISO=50`, `request=1 ... EXTRA_SHORT`, `request=2..4 role=LONG`.
Пришли `resultFrame=86 role=EXTRA_SHORT timestamp=128156696749221` (+468.9 мс от cutoff) и `resultFrame=87 ...
timestamp=128156763292346` (+535.5 мс), между ними 66.5 мс = 2 × `frameDurationNs=33333333` [вывод из чисел лога].
Значит ultrashort-кадры отстоят от базы на ~0.5 с — отсюда важность проверки движения (§3.4). В серии воркера они
получили индексы 33 и 34 (0 база, 1..29 N, 30..32 L) — `hybrid burst: frames=35 base=28 ... normals=30 bracketed=3
ultrashort=2` (`base=28` — номер кадра кольца, не индекс) [лог].

### 1.6 Проверка коэффициента усиления (HYBRID GAIN CHECK / gainMeasured)

Фактор k и вся нормировка ultrashort (гайд выравнивания, маска, вес и усиление в слиянии) берутся из `exposure` кадра,
поэтому до слияния проверяется, совпадает ли отношение по метаданным с данными (P27, `gainMeasured`, умолчание 1, `H:261-266`):

* `hybridApplyMeasuredGains` вызывается в начале `hybridReconstruct`, если в серии есть роли 3/5 (`H:4769-4782`): слияние
  перезапускается с исправленными `exposure` и `gainMeasured = -1` [код].
* Измерение одного кадра `hybridMeasuredGain` (`H:4631-4667`): сетка до 32×32 тайлов 16×16 RAW; тайл учитывается, если ни в
  одном из двух кадров нет отсчёта `≥ 0.98·white` (сырые коды), сигнал на шкале базы `s = (mb + mo/expected)/2` даёт тёмному
  кадру ≥ 8 DN (`s·min(1, expected) ≥ 8`) и яркому ≤ 80 % диапазона, а отношение тайла `mo/mb` лежит в 0.5..2 × метаданных.
  Нужно ≥ 64 тайлов; результат — медиана; `mad` — медиана |отклонений| / медиана; кадр «ok» при `mad < 0.15` (`H:4665`).
  Порог берётся по `s`, а не по среднему тёмного кадра: тест по собственному среднему завышал тусклый ultrashort на +34..37 %
  (vivo X200 Ultra, Tetra 10x ночью; комментарий `H:4621-4629`).
* Строка `HYBRID GAIN CHECK frame=… role=… metadata=… measured=… (±%) tiles=… mad=… -> ok | metadata differs |
  inconsistent ratios` (`H:4670-4677`): «metadata differs» — если `|measured/metadata − 1| > 5 %`.
* Решение по группе (кадры одной роли с метаданными в пределах 2 %, `H:4704-4716`): кадр надёжен при `tiles ≥ 64` и
  `mad ≤ 10 %` (`kGainMinTiles = 64`, `kGainMaxMad = 0.10`, `kGainMaxMadAlone = 0.06`, `kGainMaxSpread = 0.03`,
  `kGainTolerance = 0.05`; `H:4692-4693`). Группа надёжна, если надёжных ≥ 2 и они ≥ половины группы и согласованы в 3 %, либо
  единственный надёжный — ≥ половины группы и `mad ≤ 6 %`; фактор должен лежать в 0.5..2. **Правило 5 %**: измеренный фактор
  применяется только если `|factor − 1| > 5 %` (`H:4736`), тогда **все** кадры группы получают `exposure × factor`.
  Строка `HYBRID GAIN: role=… metadata=… frames=…: X of Y reliable (...), factor F (±%) -> measured ratio used |
  metadata kept (agrees within 5 %) | metadata kept: <причина>` (`H:4738-4746`).
* При `gainMeasured = 0` — только отчёт (без изменения), строки печатаются позже (`H:5105-5110`).

## 2. Выравнивание ультракоротких кадров

### 2.1 Глобальная модель — одна обратная гомография на кадр

* Все кадры, включая ultrashort, выравниваются **одинаково**: группами по 6 к базе (`H:4955-4981`), функцией `alignment`
  (vivo CRE: детектор углов + LK + RANSAC, `SM`); при сбое CRE — глобальный сдвиг по пирамидам гайдов (`H:4961-4974`); без
  CRE — тоже глобальный сдвиг (`H:4985-5001`) [код]. Отдельного выравнивателя для ultrashort нет.
* **Нормировка усиления в гайде**: в группу передаётся `group.exposure[1+j] = frame.exposure` (`H:4958`); гайд CRE строится
  `stockMotionGuide4(raw, …, 14, 1/exposure, 0.6)` — коэффициент **`1/exposure`**, гамма 0.6 (`SM:81`, `SM:159`). Для
  ultrashort это ×k (×8, ×16, ×7.2 …): кадр подтягивается к яркости базы, но и шум тоже ×k [код]. Глобальный сдвиг использует
  ту же экспозицию в `matchScore(…, ev)` (`C:242-254`, `C:269-274`).
* **Коэффициента 1.25 нет.** В LMC 9.6 при активном Bento серый уровень пирамиды строится с `gain = 1.25·TET_base/TET_f`
  (`BentoAlignOptions.f1 = 1.25`, `AUD` §3.8 / §2.5). В SCAMERA гайд берёт ровно `1/exposure`; поиск множителя `1.25f` в
  `H`/`SM` его не находит [код: `SM:81`; поиск — отрицательный]. Осознанное ли это упрощение — в коде не записано [вывод; в
  `COMBO` §3 п.3: «применяется ли 1.25 и к самой базе — не установлено»].
* «Клиппированная база» (`ceiling = 1/exposure`) делается только для **более ярких** кадров (`exposure > 1.5`, `SM:410-420`):
  у ultrashort `ceiling = 1`, его гайд не обрезается [код]. Клиппированные области базы (именно те, что Bento заменит) в гайде
  базы плоские: углы там не находятся, гомографию задают неклиппированные части кадра [вывод].
* Невалидная гомография или подмена слота базой (`replaceFailed`) → `aligned[f] = false` (`H:4977-4979`); невыровненный
  ultrashort в Bento не участвует: выбор `us` требует `aligned[f]` (`H:5154`, `H:5160`) [код].

### 2.2 Локальное выравнивание F6 ultrashort не трогает

* F6 (тайловое LK-уточнение гомографий) по умолчанию **пропускает** ultrashort: `laUltrashort = 0` (`H:238`);
  `if(input.frames[f].role==kRoleUltrashort&&!tune.laUltrashort)continue;` (`H:5295`; потоковый вариант — `H:4914`).
  Комментарий к ключу: «x8..16 gain: noisy, isotropic 1 px kernel» — поле по шумному кадру ненадёжно, а ядро ultrashort и так
  изотропное 1 px [код]. В шейдерах `originM(f, …)` для кадров без поля читает нули (поле собирается «0 = base and frames
  without a field: zeros») — ultrashort сэмплируется строго по гомографии [вывод из кода].
* Маска Bento на CPU тоже использует только гомографию: `usH.bayerOrigin(2cx, 2cy)` с округлением до ближайшей ячейки
  (`H:3710-3711`) [код].

### 2.3 Какой «гайд» действует внутри маски

* Ядро Sabre для N-кадров — анизотропная ковариация по структурному тензору (гайд базы или собственный 6.1-тензор кадра).
  Для ultrashort этот гайд **не используется**: `if(us)Pf=vec3(kE.y,kE.y,0.0);` (`H:1242`) — изотропная гауссиана с
  `kE.y = 1/σ²`, `σ = max(0.3, bentoUsSigma)` (`H:2954-2957`). Причина (комментарий `H:1238-1240`): гайд базы видит край
  вдоль каждой границы света, его узкое поперечное σ оставляло дыры R/B одного Bayer-кадра → зелёно-пурпурная «молния».
* 6.1-окно ±1.5 px для ultrashort выключено (`(mode&2)!=0&&!us`, `H:1247`), отсечка слабых весов `kw < 0.002` к нему
  не применяется (`H:1085`, `H:1133`: `f!=0&&role!=5`) [код].

## 3. Решение Bento: выбор кадров, проверки, режимы

### 3.1 Выбор ultrashort-кадров в воркере (`H:5152-5162`)

1. `us` — выровненный кадр роли 5 с **наименьшей** `exposure` (`H:5154`).
2. Остальные кадры роли 5 присоединяются, если выровнены и их экспозиция в пределах ×1.3 от `us`
   (`|log(e_f/e_us)| < log 1.3`), пока их не больше `clamp(bentoFrames, 1, 4)`; иначе `keep[f] = false` (`H:5157-5162`).
3. Если у `us` `exposure ≥ 1` — `bento.reason = "ultrashort frame is not the shortest"` (`H:5190`; аналог LMC
   `UltrashortHasLowestTet`, но упрощённый: проверяется только `< 1`, а не «ниже TET каждого кадра») [код].
4. `tune.bento == 0` → строка `HYBRID BENTO: disabled by tuning` (`H:5258`).
5. Если Bento в итоге не применён, **все** ultrashort выбрасываются из слияния:
   `if(us>=0&&!bento.active)for(int f:usFrames)keep[f]=false;` (`H:5273`). Без Bento ultrashort не сливается вообще (как и в
   LMC: «Invalidating frame … because it is an ultra-short frame», `AUD` §3.3); кроме того, в шейдере роль 5 без Bento
   получает вес 0 (`H:1018`).

Особые пути:

* **Нативный мозаичный путь (Quad/Tetra, `mosaicPath 1`)** отбирает **один** ultrashort: `us` с наименьшей экспозицией
  (`H:6248`), и добавляет его в `pick`, только если бюджет кадров ≥ 4 (`H:6253-6257`). Второй ultrashort в серию не попадает →
  в логе `frames=1` даже при `bentoFrames 2` (§9.2) [код + лог].
* **Сплит на субкадры (`mosaicPath 0`)**: тоже один ultrashort-кадр (`H:5975`), но его b² субкадров становятся отдельными
  ultrashort-кадрами, и `vt.bentoFrames = min(4, b²)` (`H:6097`): у Quad сливаются все 4 субкадра, у Tetra — 4 из 16 [код].

### 3.2 Базовая часть маски (`bentoBase`, `H:3594-3679`) — один раз на серию

Строится заранее на пуле потоков во время выравнивания (P31: `bentoAhead`, `H:4882-4883`), если серия ≤ 16 МП
(`kHybridClassicPixels = 16000000`, `H:85`; `ahead = !large`) и в ней есть ultrashort [код]. Подробно — §4.1. Результат:
`clippedFraction` (доля клиппированных ячеек базы) и, если она `> bentoMinClipped` или `bento == 2`, сглаженная маска
(`full = true`) [код: `H:3612`, `H:3676`].

### 3.3 Проверки на ультракоротком кадре (`bentoMask`, `H:3683-3768`)

Для каждой ячейки с `mask > 0` (`H:3709`; счётчик `lm` → `maskCells`):

1. **Клиппинг самого ultrashort**: ячейка ultrashort (по гомографии, ближайшая) клиппирована, если любой из 4 отсчётов
   `≥ bentoHighlight` (0.98, в единицах **своего** кадра); счётчик `usClippedInMask`, карта `usClip` (`H:3711-3714`).
2. При `bentoLmc = 1` (умолчание) — **ошибка интенсивности LMC** (`H:3715-3735`):
   * `base3 = (R, (G1+G2)/2, B)` ячейки базы (единицы базы, 0..1);
   * `us3 = min(us·k, 1)` — «GainUp» с клампом в 1, `k = 1/usExposure` (`H:3703`, `H:3718`);
   * `error = ‖min(us3 − base3, 0)‖₂` — только там, где поднятый ultrashort **темнее** базы (движение, рассогласование;
     `H:3719-3721`);
   * `bentoValidate ≥ 2` и база в ячейке **не** клиппирована (`max(base3) < 0.98`): дополнительно
     `error = max(error, ‖max(us3 − base3, 0)‖₂)` — ultrashort заметно **ярче** неклиппированной базы — тоже движение
     («рука ушла, лампа видна насквозь»; `H:3722-3727`);
   * `error < bentoInvalid` (0.9) → ячейка валидна (`H:3728`). Иначе: `invalidCells++`, `valid[i] = clamp(1 − error)`,
     `mask[i] = clamp((1 − error)·mask[i])` (`H:3729-3731`); и если у базы `min(RGB) ≥ bentoInpaintMin (0.502)` и
     `middle(RGB) ≥ bentoInpaintMiddle (0.98)` — ячейка становится **дырой для инпейнтинга** (белая клиппированная база,
     которую нечем заменить; `H:3732-3734`).
   * Клиппированный ultrashort **не** ошибка (поднятый до 1 он ≥ базы): его ячейки остаются в маске как лучшая нижняя оценка,
     флаги клипа их отметят (комментарий `H:3695-3699`).
3. Метрики (`H:3738-3759`): `usClippedRatio = usClippedInMask / maskCells`; `largestHole` — наибольшая 4-связная компонента
   `usClip` (критерий раунда 4; при `bentoLmc` — только метрика); `inpaintHole` — наибольшая **8-связная** компонента карты
   инпейнтинга (аналог `cv::connectedComponentsWithStats` в LMC `HasLargeHoleNeedingInpainting`); поиск обрывается при
   площади > 4096.
4. **Порядок откатов, как в LMC `ShouldFallback`** (`H:3760-3766`):
   1. `clippedFraction ≤ bentoMinClipped (0.00039)` → `"not enough clipping"`;
   2. `(bentoLmc ? inpaintHole : largestHole) ≥ bentoMaxHole (15)` → `"large inpainting hole"`;
   3. `usClippedRatio > bentoMaxUsClipped (0.62)` → `"high clipping ratio on ultrashort"`.

   Проверки `HasTilingArtifacts` (LMC: компонента tiling-маски > 5, `AUD` §3.5 п.5) **нет** — `FindBlockTiles` в `H` не
   реализован (поиск `tiling|BlockTiles` по `H` пуст) [код].
5. **Режимы** (`H:3766-3767`): при `bento != 2` любой откат → `active = false`, `reason = <причина>`. При `bento == 2`
   («Всегда») проверки выполняются и сообщаются, но отката нет: `reason = "forced; would fall back: <причина>"` — как
   `force_apply` в LMC; без откатов — `"success"`. Если `clippedFraction ≤ bentoMinClipped` в авто-режиме, функция выходит
   сразу (`H:3690`), до проверок на ultrashort [код].

### 3.4 Валидация второго кадра и отказ по движению

* **Строка на каждый кадр** `HYBRID BENTO frame=<f> invalid=<N> hole=<inpaintHole> largestHole=<…> usClipped=<ratio>`
  (`H:5204-5208`).
* **Валидация (`bentoValidate ≥ 1`, ≥ 2 ultrashort, первый применён)** (`H:5209-5236`): маски остальных кадров считаются в
  режиме `bento = 2` (без отката; параллельно с первой — `otherMasks`, `H:5179-5189`; не строятся заранее при `large` или если
  у базовой части нет маски). Итоговая маска: `mask[i] = clamp(smooth[i] · max_k valid_k[i])` — сглаженная маска **до**
  проверки × валидность **лучшего** кадра: база возвращается только там, где ни один ultrashort не валиден («рука движется
  через лампу: на одном кадре она есть, на другом нет»; `H:144-148`). Плоскости `valid_k` уходят на GPU (§4.4). Строка
  `HYBRID BENTO VALIDATE: per-frame invalid cells <f>:<N> … | cells invalid in some frame=<A> in every frame (base stays)=<B>`
  (`H:5213-5235`), где A — ячейки маски с `best < 1`, B — с `best ≤ 0`.
* **Доля движения** (`H:5237-5243`): `motion = 100 · min_k(invalidCells_k) / maskCells` — по **лучшему** ultrashort-кадру
  (с одним кадром — по нему).
* **Отказ по движению** (`H:5244-5247`): `if(bento.active && bentoMotionMax < 100 && motion > bentoMotionMax)` →
  `active = false`, `reason = "motion: X % of the mask > 4 %"` + `" (refused also in mode always)"` при `bento == 2`. Это
  **единственная** проверка, отменяющая Bento и в режиме «Всегда». Умолчание 4 %; замеры (PHY110, 10 серий): рука перед
  экраном ноутбука ночью 8.1 %, статичные сцены 0..0.13 %, с рук днём с водой 2.2 % (`H:149-154`).
* **Итоговая строка** (`H:5248-5252`):
  `HYBRID BENTO: applied|not applied (<reason>) motion=<%>% of <maskCells> cells clipped=<clippedFraction>
  usClippedRatio=<…> largestHole=<…> inpaintHole=<…> invalid=<invalidCells первого кадра> checks=lmc|round4
  factor=<1/exposure_us> frames=<число ultrashort> chroma sigma=<bentoChromaSigma>`.
  `factor` печатается всегда, даже при `not applied` [код]. Клиент разбирает именно эту строку (§7.1).
* Время всего блока маски → `stats.maskMs` (`H:5164`, `H:5285`), итог `stats.bento` (`H:5286`) → `HYBRID STAGES … bento=0|1`
  (`H:5731-5733`).

## 4. Маска

### 4.1 Обнаружение клипа по ячейкам (`bentoBase`, `H:3595-3611`)

* Сетка маски — **ячейки 2×2** базы (`w2 × h2 = w/2 × h/2`), канонический RGGB (`b.canonicalRggb = true`).
* Отсчёт: `b.sample(0, x, y)` = `clamp((raw − black[фаза]) / (white − black[фаза]), 0, 1)` (`C:74-85`) — нормирован по
  чёрному/белому своей фазы, без WB [код].
* Ячейка **клиппирована**, если любой из 4 отсчётов `≥ bentoHighlight` (0.98); **близка к клипу** — если любой
  `≥ nearLevel = min(bentoNearClip, bentoHighlight)` = 0.85 (`H:3600-3608`).
* `clippedFraction = clipped / (w2·h2)` — доля **недилатированных** клиппированных ячеек (`H:3611`). Если она
  `≤ bentoMinClipped` и режим не «всегда», дальше маска не строится (`H:3612`).
* В LMC маска строится по RGB базы мягким порогом `clamp((max(r,g,b) − thr)/(1 − thr), 0, 1)` на сетке рендера
  (`AUD` §3.7, `Mask_GenerateHighlightMask`); у нас — бинарно по ячейке и по **любому** сайту (`cellClip`-логика): одиночный
  клиппированный отсчёт тоже попадает в маску (это закрывает «пробел маски» из `COMBO` §3 п.8) [код + док].
* На нативном мозаичном пути маска строится по **бинированным** кадрам (W/b × H/b), где бинированный пиксель — среднее блока
  или **белое, если клиппирован хоть один сайт блока** (`H:6288-6291`: иначе среднее клиппированных и неклиппированных
  сайтов прятало клип; реплей ×1.6: маска Bento 1.8 % ячеек вместо 5.6 %) [код].

### 4.2 Дилатация (`H:3613-3630`)

Форма — **ромб `|dx|+|dy| ≤ r` плюс внешнее кольцо квадрата (2r+1)²** — ровно форма LMC `Mask_Dilate` («octagon» в
комментарии ядра, `AUD` §3.7), r = `bentoDilate` = 4 ячейки (= 8 px сенсора). Реализация «штампом» вокруг каждой
клиппированной ячейки (P31), полосами строк на всех ядрах; результат совпадает с поиском по окрестности (форма симметрична) [код].

### 4.3 Сглаживание (`H:3631-3648`)

Сепарабельная гауссиана 7×7, `σ = max(bentoSmooth, 0.01)` = 1.0 ячейки, нормированные веса, зеркальный клэмп индексов на
краях, результат `clamp(·, 0, 1)` [код]. В LMC — то же ядро (`kernel_size = int(6σ+1)` = 7, `AUD` §3.7), но с усечением к
u8 `(int)(v·255)/255`; у нас маска **float**, без квантования [код + док].

### 4.4 Множитель «близко к клипу» (`H:3649-3675`)

Только SCAMERA (в LMC нет): карта `near` дилатируется квадратом 3×3 (r = 1), сглаживается 3-отводной гауссианой σ = 1 по
обеим осям и **умножается** на маску. Смысл (комментарий `H:3646-3650`): полоса дилатации вокруг света захватывает тёмных
соседей (резина окна рядом с белой рамой), где один ultrashort с усилением ×8..16 гораздо шумнее ~20 слитых N-кадров. После
этого шага маска > 0 только около реально ярких ячеек [код]. `maskCells` в логе считает ячейки с маской > 0 **после** этого
множителя (`H:3709-3710`).

### 4.5 Поправки по ultrashort-кадру

См. §3.3: `mask[i] *= (1 − error)` в невалидных ячейках (`H:3731`), при нескольких ultrashort — `mask = smooth · max_k valid_k`
(`H:5229`). Ячейки, клиппированные в ultrashort, остаются в маске. **Инпейнтинга нет**: дыра инпейнтинга — только метрика
отката (как и в финише LMC: «инпейнтинга в финише нет», `COMBO` §3 п.12); заполнения пикселей не происходит [код].

### 4.6 Передача маски на GPU — «u8-карта» и плоскости валидности

* В LMC карта после DilateMask и маска Bento — **u8** (вес принятия, ×255 с усечением; `AUD` эррата v4.1 п.3). В SCAMERA
  нет u8-карт: маска — `std::vector<float>` на ячейку (`BentoResult::mask`, `H:3587`), вес кадра в ячейке — `float robust[]`
  (SSBO binding 8). В u8-шкале только **счётчик** принятого веса для отчёта: `atomicAdd(sums[f], uint(clamp(r,0,1)·255 + 0.5))`
  (`H:1020`) [код].
* Хост (`H:3290-3296`): на каждую полосу строк ячеек `[cy0, cy1)` в SSBO binding 13 (`Mask`) кладутся плоскость 0 = маска и
  плоскости `1..K` = валидности ultrashort-кадров в порядке слияния (`in.maskValid`, `H:5431-5435`); размер маски проверяется
  (`size == w2·h2`), иначе плоскость нулевая. Без Bento (`bento.active == false`) `in.mask` не задаётся (`H:5430`).

### 4.7 GPU-программа `kHybDilate` (`H:980-1022`) и её uniform-ы

Одна инвокация на (ячейку `cx`, строку `cy` полосы, донор `f ≥ 1`); база (f = 0) в этой программе не участвует.

| Uniform / буфер | Значение | Где задаётся |
|---|---|---|
| `dl` (vec4) | `(dilateOffset 0.2, dilateScale 2, bento ? 1 : 0, dilateFloor 0.15)` | `H:2950` |
| `validPlanesU` (int) | `bento ? in.maskValid.size() : 0` | `H:2951` |
| `ry0, ry1, cy0, cy1` | строки сайтов / ячеек полосы | `H:3440-3441` |
| `RawR` (7) | rejection до дилатации (`kHybReject`) | — |
| `Robust` (8) | выход: вес кадра в ячейке | — |
| `Sums` (9) | счётчики принятого веса | — |
| `Mask` (13) | маска + плоскости валидности | `H:3291-3295` |
| `FrameTable.fParam[f]` | `x = 1/exposure` (усиление к единицам базы), `y = A`, `z = 1/LUTσ(A)²`, `w = роль` | `H:483-484`, заполнение `H:2826-2829` |

Логика (`H:996-1021`):

```glsl
s   = Σ_{5×5} max(1 − v − floor, 0) / max(1 − floor, 1e-3);   // v = rawR соседних ячеек
rej = clamp((s − dl.x) / dl.y, 0, 1);                          // LMC DilateMask: (Σ25 − 0.2)/2
r   = min(wc, 1 − rej) · A;                                     // wc = rawR центра
if (dl.z > 0.5) {                                               // Bento активен
    m = bmask[cell];
    if (роль == 5) {                                            // ultrashort: карта ЗАМЕНЯЕТСЯ маской
        v = 1; k = число кадров роли 5 с индексом < f;
        if (validPlanesU > 0 && k < validPlanesU) v = bmask[(k+1)-я плоскость][cell];
        r = m · A · v;
    } else r *= (1 − m);                                        // N и L: исключаются из светов
} else if (роль == 5) r = 0;                                    // без Bento ultrashort не сливается
robust[f][cell] = r;  atomicAdd(sums[f], round(clamp(r,0,1)·255));
```

Диспетчеризация: `dispatchRows(dilateProgram, w2, cy1−cy0, frames−1, …)` (`H:3442`). Rejection самого ultrashort
(`kHybReject`) считается, но затем полностью перезаписывается — он не нужен (как `rej_us := mask` в LMC, 0x3bf3c88) [код + док].

| Кадр | Вес в ячейке с маской m |
|---|---|
| база (f = 0) | `wb = 1 − m` (`H:1225`); 0 при `debugFrame ≥ 0` или `noBase` (`H:1226`) |
| N, L (роли 1, 3) | `r = min(wc, 1 − rej) · A · (1 − m)` |
| ultrashort (роль 5) | `r = m · A_us · v_k`, `A_us = bentoUsWeight / |usFrames|` (`H:5414`) |

Это ровно семантика LMC 9.6 по эррате v4.1: `rej *= 1 − mask` для **всех** кадров, **включая базу**, и `rej_us := mask`
(`AUD` эррата п.3; `COMBO` §3 п.8б). Внутри маски (m = 1) сливаются **только** ultrashort-кадры; на размытой границе маски —
линейная по весам смесь; вне маски ultrashort не участвует [код + док]. Пиксели (а не ячейки) берут m своей ячейки
(`bmask[(cy−cy0)·w2+cx]`, `H:1217`) — маска постоянна на квадe 2×2 сенсора (на сетке 2× — на 4×4 выходных пикселях) [код].

Нюанс относительного веса на границе: итог цвета = `Σ r·kw·v·g / Σ r·kw`, т.е. ultrashort и N соревнуются не только r, но и
суммой ядра `Σkw` (у N — узкие анизотропные ядра Sabre по ~20 кадрам, у ultrashort — изотропное σ = 1 px по 1–2 кадрам)
[вывод из формулы].

### 5.2 Усиление и единицы выхода

* `fParam[f].x = 1/exposure` (`in.gain.push_back(1.f/t)`, `H:5420`): каждый отсчёт ultrashort умножается на k
  (`a.num[c] += r·kw·v·g`, `H:1098`). Выход слияния остаётся **в единицах базы** («Output stays in base-frame units, so
  highlights run above 1.0», `H:11-13`; `H:16-18`). Это «равноправный вариант» из `COMBO` §3 п.10: TET_ref = TET_base,
  ultrashort с усилением k, один набор uniform-ов для гайда и слияния [код + док]. В LMC 9.6 наоборот: TET_ref = TET_us,
  `input_gain[base] ≈ 1/k`, а фактор k применяется в финише (`AUD` §3.5 п.7, §3.6).
* Выход — `float` RGB без клампа (`out`, `H:2802-2806`); при клипе ultrashort значения доходят до ≈ 0.98·k (§5.4).
  Пример: `NICE RGB: mean=0.052637 max=1.261846` на снимке 14:01:40 [лог].
* Объединённый Bayer-DNG (`mergedDng`) клампит RGB в [0, 1] (`H:5673`): **света Bento в DNG теряются** [код].

### 5.3 Ядро ultrashort-отсчётов

* `Pf = (kE.y, kE.y, 0)`, `kE.y = 1/σ²`, `σ = max(0.3, bentoUsSigma)` = 1 px сенсора (`H:1242`, `H:2954-2957`).
* `kernelW(d, P) = exp2(−0.72135·dᵀPd) + kernelFloor` = `exp(−|d|²/(2σ²)) + 5e-5` (`H:1056-1058`, `0.72135 = 0.5/ln 2`).
* Сайты: для каждой из 4 фаз CFA — 2 сайта решётки по каждой оси вокруг позиции O (`H:1077-1081`), без 6.1-окна и без
  отсечки `kw < 0.002` для роли 5 (`H:1085`) [код].
* На сетке 2× ядро остаётся в пикселях сенсора, слияние идёт по 4 подпозициям ±0.25 px (`H:1218-1222`, `H:3467-3471`) [код].
* В LMC вместо этого ядро **базы** расширяется в `S = 2.5` раза по всему кадру (`BentoOptions.f9`, `AUD` §3.8, `COMBO` §3
  п.13), а линейное ядро `linear_kernel_mask` действует только в `spatial_bayer`, не в `spatial_rgb` (`AUD` §3.5 п.6). Мы
  ядро базы не трогаем (внутри маски у базы вес 0), а ядро ultrashort делаем изотропным σ = 1 px: один Bayer-кадр требует
  ≥ ~0.7 px, иначе дыры R/B («LMC: base kernel x2.5 under Bento», `H:142-143`) [код + док].
* Нативный мозаичный путь: `Pf = (kE.y, kE.y, 0)` пересчитывается в нативные пиксели множителем `natK.x = 1/(b·ks)²` и
  клэмпом `natClamp` (`H:1994`, `H:1999`; `natK` — `H:3038`): σ в нативных px ≈ `bentoUsSigma · b · ks` с поправкой
  клэмпа (Tetra ночью ks = 1 → ≈ 4 нативных px = 1 бинированный px) [вывод из формулы; точная граница клэмпа не проверялась].

### 5.4 Суммы с учётом клипа (clipNum / clipDen)

`frameSamples` (`H:1074-1101`), `frameSamplesPlain` (`H:1122-1144`):

* Отсчёт с флагом выброса (бит 0 слова сайта) — пропускается.
* Отсчёт клиппирован, если флаг ячейки (бит 1, `cellClip`: любой сайт ячейки ≥ `clipLevel`, программа `kHybMark`,
  `H:797-825`) или `v ≥ clipLevel` (0.98, в единицах **своего** кадра). Клиппированный отсчёт:
  * роль 3 (L) — пропускается совсем («нижняя граница ниже базы»);
  * иначе идёт в `clipNum[c] += r·kw·v·g`, `clipDen[c] += r·kw`; для роли 5 ещё `usClip += r·kw` (`H:1088-1096`).
* Цвет пикселя (`H:1257-1266`): `num/den`, если есть неклиппированные отсчёты; иначе **клиппированное среднее**
  `clipNum/clipDen` (бит c флагов); иначе `baseFill` (решётка базы). Бит 3 — если в окне был исключён клиппированный отсчёт (`H:1265`).
* Следствие для Bento: клиппированный ultrashort даёт клиппированное среднее на уровне ≈ `0.98·k` («clip at k x white instead
  of 1 x white», `H:5702-5703`) — это бит 5 (§5.6). Внутри маски, где ultrashort не клиппирован, значения — реальные данные
  ultrashort×k [код].

### 5.5 База в маске и рядом с ней

* `wb = 1 − m`; при `m ≥ 1` база не сэмплируется вовсе (`if(wb>0.0)`, `H:1251`).
* 6.1-окно у базы выключено, где `m > 0` (`(mode&2)!=0&&m<=0.0`, `H:1255`) [код].
* Счётчик принятых доноров `frames` ultrashort не учитывает (`if(!us)frames+=rw`, `H:1246`); значит на краю маски, где N
  отброшены `(1 − m)`, срабатывает расширение ядра базы (6.1: ×1.826 по σ ниже 4 кадров) [вывод из кода].

### 5.6 Карта эффективных кадров и трейлер флагов клипа

* **Карта эффективных кадров**: `eff = a.cover + wb` (`H:1270`); `a.cover += rw·kw` по зелёным отсчётам **всех** кадров,
  включая ultrashort (`H:1099`; для него `rw = r/A = m·v`). Внутри маски покрытие ≈ покрытию 1–2 ultrashort → низкий код
  карты → сильнее шумодав (§7.5). Кодирование: `code = clamp(round(eff · 64/median), 1, 255)` (`H:5680-5697`) [код].
* **Доля принятого веса** `robustShare[f] = sums[f] / (255 · w2·h2)` (`H:3504-3505`) → строка `HYBRID MERGE FACTORS`; у
  ultrashort ≈ доля площади маски × A, поэтому печатается `0.00` [код + лог].
* **Флаги клипа** (uint8 на выходной пиксель; пишутся, если трейлер запрошен или включён rim-проход; `H:1271-1290`):

| Бит | Значение | Где ставится |
|---|---|---|
| 0, 1, 2 | R / G / B взят из клиппированного среднего | `H:1260` |
| 3 | рядом исключён клиппированный отсчёт (граница клипа) | `H:1265` |
| 4 | пиксель внутри маски Bento (`m > 0`) | `H:1272` |
| 5 | клиппированное среднее содержит ultrashort (`usClip > 0` и любой из битов 0–2): уровень клипа k·white | `H:1273` |
| 6 | бит 3 и rim-проход отработал (цвет края — работа воркера) | `H:1284` |
| 8–13 | кандидат rim-прохода (доля исключённого веса ×63; во внутреннем буфере, в трейлер не попадает) | `H:1276-1282` |

  Трейлер: тот же размер/сетка/сдвиг начала CFA, что и карта эффективных кадров; отчёт (`H:5705-5724`):
  `HYBRID CLIP FLAGS: trailer WxH uint8 (bits R,G,B clipped mean, border, Bento, ultrashort) R= G= B= border= bento=
  ultrashort= [rimChecked=]` — счётчики пикселей по битам 0–6 [код]. Клиент проверяет размер ответа точно (`VNC:490-500`)
  и кладёт трейлер в `VivoNiceRgb.lastClipFlags` (`VNC:555`).

## 6. Цвет Bento (`bentoChroma`), нативный мозаичный путь, взаимодействие с rim-проходом

### 6.1 Зачем цветовой проход

С ядром σ = 1 px внутри маски R и B каждого выходного пикселя берутся из ближайших R/B-сайтов (каждый второй ряд/столбец)
одного-двух Bayer-кадров: вдоль наклонного края света R и B «шагают» каждые 2 px относительно G — оранжево-синий пунктир
(есть уже в простом демозаике RAW) (`H:158-161`). Проход `kHybBento` перестраивает R и B внутри маски как
`G_merged × (R/G, B/G)` ultrashort-кадров на **широком** изотропном ядре σ = `bentoChromaSigma` = 2 px (`H:1365-1368`) [код].
Эффект: «pair-2 sill: 32 % → 7 % пикселей края Bento со ступенькой цвета > 0.1; при силе 1.0 — 11 %» (`H:162-164`) [док в коде].

### 6.2 Программа `kHybBento` (`H:1369-1404`) + `usWide` (`H:1185-1206`)

* Компилируется только если `bento > 0 && есть ultrashort && bentoChromaSigma > 0 && bentoChroma > 0` (ранний контекст —
  `H:4834`; при слиянии — `H:5547-5557`, контекст пересоздаётся, если в нём нет программы); тело =
  `RIM_STATS + BENTO_PASS + kHybMergeCommon + kHybBento` (`H:2760`).
* Uniform-ы (`H:2958-2965`): `kE = (debugFrame, 1/σ_us², 1/σ_c², clamp(bentoChroma, 0, 16))`, `kG = (grid, ow, 0, 0)`,
  `mergeModeU = (mergeMode, noBase, флаги записаны слиянием ? 1 : 0, 0)`; на полосу — `cy0, cy1, ry0` (`H:3478-3481`).
* Порядок на полосе: слияние (все подпозиции) → `kHybChroma` → **`kHybBento`** → `kHybRim` (`H:3466-3487`: слияние 3466-3471, chroma 3473, Bento 3478, rim 3483) — Bento-проход
  до rim, так как rim читает слитый цвет.
* Алгоритм на выходной пиксель:
  1. `m = bmask[cell]`; при `m ≤ 0` выход (`H:1377`).
  2. По кадрам ячейки: `wo = (1 − m) + Σ r` не-ultrashort, `wu = Σ r` ultrashort; для каждого ultrashort `usWide`:
     сайты решётки **±2 по оси и фазе** (4×4 на фазу, `dj, di ∈ {−2, 0, 2, 4}`), вес `r·exp(−|d|²/(2σ_c²))`, клиппированные
     сайты (флаг ячейки или `v ≥ clipLevel`) копятся отдельно в `uClip[c]` (`H:1189-1206`, `H:1385-1394`).
  3. Выход, если `wu ≤ 0`, нет зелёного или **у ultrashort есть клиппированный зелёный в широком окне** (`uClip.y > 0`) — там
     цвет перестраивает `kHybRim` (`H:1395`).
  4. `s = min(bentoChroma · wu/(wu + wo), 1)` — доля ultrashort в пикселе ×4: на гладком крае маски ~20 доноров и база
     забирают вес (`H:1398`).
  5. `R ← mix(R, G·(uR/uG), s)`, если у R нет клиппированных ultrashort-сайтов и R не клиппированное среднее (бит 0); так же B
     (бит 2): клиппированное среднее — нижняя граница для восстановления светов, его не трогают (`H:1400-1403`).

### 6.3 Почему на нативном мозаичном пути (Quad/Tetra) цвет Bento выключен

* `hybridReconstructMosaicNativeMerge` принудительно ставит `chromaDiff = 0, rimRatio = 0, bentoChroma = 0` с отчётом
  `HYBRID MOSAIC NATIVE: colour-difference, clip-border and Bento colour passes off (they work on the binned frames; native
  variants not built)` (`H:6340-6346`); в `merge()` ещё и исключение, если какой-то из них всё же включён для нативного слияния
  (`H:3000-3001`).
* Причина (`H:292-295`, `H:1801-1806`): эти проходы пересэмплируют **бинированную** базу в бинированных позициях
  (`(ox + 0.5)/b − 0.5`), а нативное слияние пишет позиции `ox − (b−1)/2` — на полпикселя (Quad) в сторону, и корректирует
  суммами бинированной базы, которые нативное слияние никогда не накапливало (ревью P29: chroma на Quad, один кадр — края
  −1.2 дБ, плоский шум +8 %). Нативные варианты не построены [код].
* Следствие: на нативном пути внутри маски R/B ultrashort — с ядра `Pf` одного кадра (второй ultrashort туда не попадает,
  §3.1), пунктир и цветная кайма на краях светов возможны; их ловят только постпроцессы `nicergb`/`clipband` (§7). Пример
  из памяти проекта: «purple artifact on left window» = нативный путь, проходы края/цвета Bento выключены, R клипует на 0.96 →
  сиреневое небо и голубая сетка; исправлено в `nicergb` (нейтральный белый при одном измеренном канале) — коммит hl2
  5b5b35e [док: memory].
* Сплит на субкадры (`mosaicPath 0`) цветовой проход **не** выключает (меняются только `grid`, `mosaicBlock`, `caCorrect`,
  `bentoFrames`; `H:6096-6097`) [код].

### 6.4 Взаимодействие с проходом края клипа (`kHybRim`) и `kHybChroma`

* `kHybRim` (`H:1411-1565`) повторяет суммы слияния (тот же `wb = 1 − m`, то же ядро ultrashort `kE.y`, `H:1477-1500`) и
  перестраивает R/B из отношений реальных (неклиппированных) сайтов вокруг; ultrashort всегда входит в отношения (шаг
  `rimStride` к роли 5 не применяется, `H:1514`). Кандидаты — только пиксели с настоящим зелёным (`a.den[1] > 0`); где зелёный
  ушёл в клиппированное среднее (внутренность света), цвет оставлен восстановлению светов и дефринжу (комментарий
  `H:1274-1278`).
* Разделение труда с Bento-проходом: Bento-проход работает там, где у ultrashort нет клиппированного зелёного; где он есть —
  rim (`H:1365-1368`, `H:1395`).
* Внутри Bento-света бит 3 стоит почти везде (клиппированные отсчёты базы с весом `1 − m` на краю маски, округление маски
  или маска, пониженная ошибкой LMC), поэтому `nicergb` по биту 6 отключает свой сплошной дефринж: раньше он делал синий экран
  монитора белым (c_12: 102,141,212 → d_12: 220,222,233) (`NRGB:124-127`, `H:1283-1284`) [код + док в коде].
* `kHybChroma` (цветоразностная интерполяция базы) работает только на доле базы (`wb = 1 − m`, `H:1308`) — внутри маски её
  доля 0 [вывод из кода].

## 7. Постобработка: что делает приложение с результатом Bento

### 7.1 Состояние Bento на стороне Java

* После чтения ответа воркера (`VNC:501-504`):
  `LmcHybridBurst.lastBentoApplied = report.indexOf("HYBRID BENTO: applied") >= 0`,
  `lastBentoFactor = число после "factor="` в этой строке (умолч. 1), `lastBentoUsClipped = число после "usClippedRatio="`
  (умолч. 0) — разбор `reportNumber` (`VNC:585-592`). Т.е. Java узнаёт k **из лога воркера**, а не из метаданных [код].
* Трейлер флагов → `VivoNiceRgb.lastClipFlags` (`VNC:555`); в начале каждого слияния и при CPU-откате всё сбрасывается
  (`VNC:501`, `LHB:799-802`).
* `PreferenceKeys.isHybridShot() || lastBentoApplied` включает гибридную ветку постпроцессинга (`VNR:347-348`).

### 7.2 Поканальные уровни клипа (`VivoNiceRgb.channelClip`, `VNR:119-198`)

Статистика по каждому 17-му пикселю, по каждому каналу камеры (до WB и затенения) [код]:

* гистограмма значений в `[0.80, 1.10)` ожидаемого белого (бин 0.002) — для уровня базы `lo`;
* при `bento && k > 1` — вторая гистограмма `v/k` — для уровня ultrashort `hi` (`VNR:140`, `VNR:171`);
* `useLo = !bento || flags` (`VNR:170`): в Bento-снимке без флагов уровень 1.0 не используется вовсе — реальные данные
  ultrashort плавно проходят через 1.0 и не должны считаться клипом (`VNR:112-117`);
* `lo` = положение «плато» (самое плотное окно 1 % в `[0.92, 1.03)`, должно в ≥ 6 раз превышать фон `[0.80, 0.90)`), иначе
  номинал 1.0 (`VNR:175-179`, `plateau()` `VNR:84-105`);
* `hi` = плато `v/k` в `[0.90, 1.08)` × k; без плато — `k`, если ultrashort где-то клиппирован (`usClipped > 0`), иначе 0 —
  уровень выключен («No plateau and the ultrashort never clipped: nothing in the data reaches k», `VNR:180-186`);
* уровень используется для всех трёх каналов или ни для одного (`VNR:191-193`; `VNR:192-193`); `nearClip`, если максимум канала
  ≥ 0.85 уровня (`VNR:194-195`) — тогда строятся локальные цветовые блоки 8/32/128 (`hlrecovery/chanprep` + 2× `reduce`).
* Лог: `highlight recovery per channel: strength=… bento=… k=… usClipped=… flags=… lo=…(nominal|plateau) hi=…(off|nominal|plateau)
  max=… samples=… nearClip=… clipWhite=… ms=…` (`VNR:398-401`).
* `lastClipWhite = max_c(top[c] / whitePoint[c])`, `top = hi`, если `hi` включён, иначе `lo` — уровень клиппированного белого
  после WB; `lastRealClip = cc.enabled()` (`VNR:391-397`).

### 7.3 Восстановление светов в `nicergb` (`NRGB:35-48`, `NRGB:118-237`)

Уровень клипа **на пиксель** выбирается по флагам воркера (`levelAt`, синхронно с `hlrecovery/chanprep.glsl:23-35`):

| Флаги пикселя | Уровень |
|---|---|
| нет флагов (без трейлера) | `hi`, если включён, иначе `lo` |
| биты 0–3 пусты | клипа нет (`vec3(−1)`) — значение не трогается |
| бит 5 (клиппированное среднее с ultrashort) | `hi` (k·white), иначе `lo` |
| биты 0–2 (клиппированное среднее базы) | `lo` (white), иначе `hi` |
| только бит 3, внутри маски (бит 4) | `hi` или **нет клипа**: внутри Bento значение — данные ultrashort (до k); исключённые отсчёты базы (вес `1 − m`) про него ничего не говорят |
| только бит 3, вне маски | `lo`, иначе `hi` |

Дальше (`NRGB:136-237`): дефринж краёв (бит 3; при бите 6 сплошной дефринж не делается), оценка клиппированного канала через
локальный свет (нижняя граница, только вверх), «нейтральный белый при одном измеренном канале», при клипе всех трёх — нейтральный
белый на уровне `max(r, top)`; смешивание с силой `highlight_recovery/100` [код]. Узел `HighlightRecovery` для гибрида/Bento
пропускается (`HighlightRecovery.java:56-62`: «per-channel recovery in VivoNiceRgb»). Пост-проход `vivohdr/clipband.glsl`
(сила `highlight_band`) гасит оранжево-синий пунктир края клипа по флагам (комментарий `clipband.glsl:1-12`: у ArkCam его нет,
потому что «the Bento frame covers the band») [код].

### 7.4 ARK-тон и запас по светам

* `ArkStats` строит `arkLow` (½ сетки, полное затенение линзы) **без клипа**: «Bento content above 1 stays»; потолок `clip`
  берётся из максимума данных, не больше 4 (`ArkStats.java:21-27` (javadoc)).
* `ArkAe`: `r.bento = gmax > 1.05` (`ArkAe.java:148`) — флаг `bento=1` в строке `ARK SMART_HDR_STAT` означает «данные выше
  1.05», а не «воркер применил Bento» [код]. `ArkFusion`: `bracket_denoise` диапазона Bento (`clip > 1.05`, `ArkFusion.java:15`).
* `ArkCombine`: потолок/плечо Bento только при реальном запасе: `headroomU = VivoNiceRgb.lastRealClip ||
  LmcHybridBurst.lastBentoUsClipped > 0` (`ArkCombine.java:102-103`).
* Значения > 1 в цепочке: воркер их не клампит (§5.2), `nicergb` в гибриде принимает знаковый вход без клампа
  (`VNR:200-210`, `signedU`), ARK сжимает их тоном. В объединённый DNG они не попадают (кламп `H:5673`) [код].

### 7.5 Шумодав по карте эффективных кадров

Внутри маски эффективных кадров мало (1–2 ultrashort), поэтому `lmcdn/strmap.glsl` усиливает шумодав:
`f = clamp(sqrt(E_ref / E(p)), 1, effMax)²`, `effMax = bento_denoise_max` = 3 (`strmap.glsl:5-19`, `LmcDenoise.java:366`,
`LmcDenoise.java:527`; в NLM-маршруте то же — `NiceDenoise.java:105`, `NiceDenoise.java:208`; `XML:88`, 1..12). Комментарий
прямо называет случай: «Bento regions merged from one gained frame» [код].

### 8.3 Известные ограничения и открытые вопросы

1. **Движущиеся света.** Ultrashort снимаются **после** кольца: в логе +357…+536 мс от новейшего N (§1.5, §9). Всё, что
   движется за это время, ловит только проверка интенсивности (ошибка ≥ 0.9 — грубая) и отказ по движению (4 %). Ниже порога
   невалидные ячейки получают `mask·(1 − error)` — база с клиппированными данными частично возвращается внутрь света
   (пятнистость) [вывод из кода]. F6 к ultrashort не применяется (`laUltrashort 0`): параллакс и локальные сдвиги внутри
   света не исправляются [код].
2. **Ночной экран / клипующий ultrashort.** Память проекта (2026-10-04): текст экрана ноутбука клиппирован в N, ultrashort
   ещё 17 % клиппирован, Bento «Всегда» → испорченный текст; предложено недоэкспонировать N ночью как ARK. В авто-режиме при
   `usClippedRatio > 0.62` был бы откат; в «Всегда» клиппированный ultrashort остаётся (нижняя граница на уровне k·0.98) [док:
   memory, код].
3. **Пятна на лампе (история).** «Artifacts on light» (vivo, plain Bayer, Bento forced, usClipped 0.75): пятна давало
   поканальное восстановление светов (блочная статистика + пороги + переключение уровней lo/hi по флагам), исправлено в
   `nicergb`/`clipband` (ec0dcd7, затем hl2 5b5b35e: нейтральный белый при одном измеренном канале, подавление
   пурпурно-голубой каймы); оставшиеся тёмные пятна на лампе — реальное отражение, есть в одиночном RAW базы [док: memory
   `pending-user-tasks.md`].
4. **Цветная кайма на краю маски.** Цветовой проход Bento снижает её (32 % → 7 %), но на **нативном мозаичном** пути
   (Quad/Tetra, режимы vivo с принудительным sensor mode) проходы цвета Bento, края клипа и цветоразностный выключены (§6.3),
   и сливается только **один** ultrashort (§3.1) — кайма и шум ×k там больше; остаётся только постобработка [код + вывод].
5. **Фактор на упоре выдержки.** На ярких сценах N уже около минимальной выдержки: заказанный factor 16 превращается в
   ×7.2 (§9.2), запас по светам меньше; при отношении ≥ 0.5 кадры не снимаются вовсе («us skipped (sensor floor)») [код + лог].
6. **Разные пороги в разных местах.** Триггер плана — сырые коды ≥ 0.95·white без вычитания чёрного (`CC:3665`); маска
   воркера — 0.98 после чёрного (`H:133`); `bentoMinClipped` считается по недилатированным **ячейкам** (`H:3611`), а LMC —
   по ненулевым пикселям своей highlight-маски; `bentoMaxHole = 15` — в **ячейках** (15 ячеек ≈ 60 px сенсора), у LMC — в
   пикселях маски [вывод: единицы различаются; эквивалентность не проверялась].
7. **Гайд выравнивания ultrashort** — `1/exposure` без 1.25 LMC и без отдельной проверки качества гомографии, кроме
   `validate()`; шум ×k в гайде [код].
8. **DNG.** Объединённый DNG клампит в [0, 1] — света Bento в нём теряются (`H:5673`); память проекта отмечала это как
   открытый пункт («DNG loses Bento highlights») [код + док].
9. **Маска на ближайшей ячейке.** Проверка ultrashort в `bentoMask` берёт ближайшую ячейку по гомографии, без субпиксельной
   интерполяции (`H:3710-3713`) — на резких краях ошибка интенсивности завышается/занижается на полпикселя [вывод].
10. **Режим «Всегда» на vivo в логах этого дня.** Тюнинг `bento 2.0` (§9): Bento применяется даже при 0.0037 % клиппированных
    ячеек — маленькие маски из шумного ×k кадра; проверка «not enough clipping» только сообщается [лог + код].

### 9.3 Для сравнения: авто-режим на Pixel (`P7`, 14:50:54)

`hybrid plan: N=14.956ms*ISO195 clip=0.0009 requests=[EXTRA_SHORT 7.756ms*ISO47 (x0.125) ×2, LONG … ×5]` — здесь Bento
снят по **триггеру** (0.0009 > 0.0005): ISO снижен с 195 до минимума 47, выдержка `14.956·195/(8·47) = 7.756 мс`, ratio 0.125.
`HYBRID GAIN: role=5 metadata=0.1250 … factor 0.9784 (-2.2 %) -> metadata kept`; `HYBRID BENTO: applied (success) motion=0% of
31008 cells clipped=0.000604 …` — 0.000604 > 0.00039, откатов нет, «success»; `factor=8.000170 frames=2`; трейлер
`bento=124032 = 31008 × 4` (сетка 1×: ячейка = 2×2 выходных px) [лог + вывод]. В серии без клипа (`clip=0.0000`) план пишет
`no clipping (0.0000)` и ultrashort не снимаются [лог].
