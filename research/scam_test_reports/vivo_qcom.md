# vivo_qcom findings

## P1 vivo X300 Ultra: V2547A (PD2547 CN, A17) and V2562 (global, A16) - In-sensor zoom on the 200 MP main (cam 3) and tele (cam 5): CROPPED_RAW is set already, but the Qualcomm ISZ session key is never sent
- theme: ISZ
- confidence: verified (keys/config); HAL behaviour at zoom>1 inferred
- evidence: characteristic android.scaler.availableStreamUseCases long[] includes 6(CROPPED_RAW) on cams 0/2/3/4/5 (A 2840/7312/9331/11565/13822; B 2723/7171/9183/11404/13650). characteristic pixelArraySizeMaximumResolution = 16320x12256 (cam 3) and 16320x12288 (cam 5); binningFactor reports 2x2 although the real ratio is 4 (A 9765/9772/14150/14157). Session keys org.codeaurora.qcamera3.sessionParameters.EnableInsensorZoom / EnableSnapshotOnlyInsensorZoom / ExtendedMaxZoom (A 3710/3714/3720, B 3593/3597/3603). File /vendor/etc/camera/camxoverridesettings.txt: enable4x4InSensorZoom=1, enableInSensorZoomForOnlyPhysicalStream=1, AECGainThresholdForQCFA = 30.0, enableSensorRemosaic=0 (A 22799/22789/22729/22690; B 22491/22481/22421/22382). Selector ROIREMOSAIC = [ROI, QuadCFA, NORemosaic] (A 26334). Results at 1x: rawBinningFactorUsed=true, rawCropRegion = full array (A 4645ff). SCAMERA: CroppedRaw.supported() sets CROPPED_RAW (CaptureController 2758). EnableInsensorZoom is only sent by XiaomiTeleZoom. SENSOR_RAW_BINNING_FACTOR_USED is never read.
- recommendation: On vivo + SOC QTI, whenever CROPPED_RAW is set, add session parameters (and repeat them in every request) org.codeaurora.qcamera3.sessionParameters.EnableInsensorZoom=1 (Integer, inferred int32) and EnableSnapshotOnlyInsensorZoom=0, so the ZSL ring frames are ISZ frames too. Test two topologies at zoomRatio 2.0: (a) physical cam 3/5 opened directly, (b) logical cam 0 with the RAW OutputConfiguration.setPhysicalCameraId("3"); the second is needed because of OnlyPhysicalStream. Expect rawCropRegion of about (1020,766-3060,2298) and rawBinningFactorUsed=false. Classify each frame with rawBinningFactorUsed + rawCropRegion and run MosaicBlockDetector on ISZ frames (a quad mosaic, NORemosaic).
- risk: Above total gain 30x (about ISO 1500) the HAL falls back to binning, so low-light ISZ frames silently become a binned crop. The payload is a quad mosaic, and HexQuadBurst.isHp9() applies the HP9 quad model to the Sony imx09e main as well. activePhysicalSensorCropRegion comes in 16320-px coordinates (A 4630). A logical RAW stream may ignore ISZ.

## P1 vivo X300 Ultra (both); index differs per firmware - Tele ROI-quad sensor mode for vivo.control.forceSensorMode is 5 on V2547A and 31 on V2562: read it from camera_config.xml
- theme: ISZ
- confidence: verified (config values); effect of forcing inferred
- evidence: File /vendor/etc/camera/camera_config.xml, CameraId 3 tele3p5x and CameraId 4 etele3p5x: <PreviewRoiQuadSensorMode> = 5 on A (21560/21572) and 31 on B (21252/21264). The tele sensor-mode table, NDK tag 0x80090000 int32[101] = {33, 3, w,h,fps...}, is identical on both phones (A 14178, B 14006). Modes 5 and 31 are both 4080x3072@30, and mode 0 is 16320x12288@7. Main table: 34 modes (A 9793, B 9645): 0 = 16320x12256@10, 1-3 = 8160x6128, 4-10/16/17/30/31 = 4080x3064@30, 26-28/32/33 = 4048x3060 (GC1). Session/request key vivo.control.forceSensorMode is listed (A 3788, B 3671); on the PD2454, 5 gives 2x Quad and 7 gives 4x Tetra (ModuleRegistry).
- recommendation: For an X300U tele 2x ISZ module, parse PreviewRoiQuadSensorMode from /vendor/etc/camera/camera_config.xml at runtime (world-readable) and send it as vivo.control.forceSensorMode (session + request). Do not reuse the PD2454 values 5/7. The main has no such entry: find its ROI index with a DcgSearch-style sweep (one candidate per session over 4..10, 16, 17, 30, 31) and keep the hit keyed by Build.FINGERPRINT. Accept a hit only when FovSelfCheck reports field 1/2.00 and MosaicBlockDetector reports block 2.
- risk: Indices change between firmwares (proven by A vs B). Index 0-3 (16320/8160 modes) under a 4080 RAW stream may stall or scale. The key has not been tried on the X300U under AppType DEFAULT.

## P2 vivo X300 Ultra (both) - ImageReader maxImages 63 aborts the process natively; the RAW ZSL ring holds 30 fps up to depth 58
- theme: ZSL
- confidence: verified
- evidence: 'ImageReader.newInstance accepts maxImages <= 62 (at 63: process aborted (native))' for RAW_SENSOR, YUV and PRIVATE (A 4968-4979, B 4840-4851). Ring search on RAW 4080x3064 at 30 fps: 58 OK, 59 drops to 22-24 fps (A 4980-4995, B 4852-4866; also cams 3/4/5, A 11461ff/13718ff/15843ff). Camera 0: maxNumOutputRaw 1, pipelineMaxDepth 8. SCAMERA CaptureController 2455-2456 sizes the reader as min(zslRingCapacity()+3, 103) when the ring is YUV or zsl_memfd_ring is 0, and scam_dev zsl_reader is unbounded up to 103. The ZSL pref goes up to 100 (PreferenceKeys 1381).
- recommendation: Before every ImageReader.newInstance on this device (and possibly on all Qualcomm vivo phones), clamp maxImages to ≤62. For a 30 fps RAW ring, clamp to ≤58. Clamp the ZSL-buffer pref the same way.
- risk: The crash is native and cannot be caught, so the clamp must happen before the call. Default settings (memfd ring, reader 20; YUV ring 53) are safe today. The risk is in user and dev settings.

## P2 vivo X300 Ultra (both) - The HAL's short/long AEC pair (org.quic.camera2.statsconfigs.*) is readable by third-party apps and gives the scene's HDR EV gap
- theme: AE/ISO
- confidence: verified (values/relations); semantics inferred
- evidence: Result keys in every preview and RAW result: AECExposureTime long[3], AECLinearGain float[3], AECSensitivity float[3], AECCompenADRCGain, AECCompenDarkBoostGain, AECLuxIndex, plus org.codeaurora.qcamera3.stats.is_hdr_scene byte. A cam 0: exp {10, 20, 20} ms, gain {87.06, 161.87, 154.16}, ADRC 3.542, DarkBoost 1.050 (A 4686-4690). B cam 0: {10, 10, 10} ms, {8.78, 31.79, 21.56}, ADRC 2.455, DarkBoost 1.474 (B 4564-4568). exp[1]*gain[1]/(exp[0]*gain[0]) = ADRC×DarkBoost exactly (A 3.719, B 3.619, about 1.9 EV). android.sensor.sensitivity ≈ 50×gain[0] (A 4334, B 439, front 6714). SCAMERA reads none of them (grep statsconfigs: 0 hits).
- recommendation: Read these keys on each preview result on Qualcomm vivo (and other CamX phones). Use log2(ADRC×DarkBoost) as the HAL's EV gap between the RAW N frame (the highlight-protected short exposure) and the mid-tone target. Use it to size the L frame and the tone lift of the merge. Use is_hdr_scene as the HDR trigger and AECLuxIndex for night thresholds.
- risk: Index semantics (0 short, 1 long, 2 safe) follow the CamX convention (inferred). The sensitivity result is capped: on cam 3 at night, gain[0] 169 (ISO-equivalent 8459) was reported as ISO 4551 (A 11242ff), so frames are darker than the AE target.

## notes
Both reports are the vivo X300 Ultra (SM8850). SCAMERA already names V2562 so in ForcedStabilization; V2547A is the PD2547 CN build on Android 17, V2562 the global build on Android 16. The dumps ran unspoofed as com.scam.test, so static vendor tags appear only as NDK ids. Request, session and result vendor keys have names.
